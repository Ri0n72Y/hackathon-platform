# LabourChain 五页面布局设计 · Inter-Knot × 蓝紫主题 D2

> **Product Interface Designer｜2026-11-13**
>
> **确认依据：** 产品方在对话中查看四页切换式暗色布局草案及第五页 Topic Page 示意后，明确要求「按照这个布局，写入设计 design」。因此本文件把**五个页面的布局方向与信息层级**写为当前 D2 设计方案。
>
> **验证边界：** 这是静态页面结构与视觉布局规范，不代表代码实现、截图像素还原或 D4 浏览器测试完成。各数值为设计建议，真实页面上仍需用户校准。项目范围依 [#2](https://github.com/Ri0n72Y/hackathon-platform/issues/2)，Topic Page 行为依 [#31 最新决定](https://github.com/Ri0n72Y/hackathon-platform/issues/31)；[ #3 平台级 Topic 流](https://github.com/Ri0n72Y/hackathon-platform/issues/3) 是不同的后续模块。

## 1. 五个路由与页面职责

| 页面 | 路由 | 核心阅读 / 操作目标 | D2 主布局 |
| --- | --- | --- | --- |
| 项目主页 | `/{owner}/{repo}` | 理解单个 GitHub 仓库、认识团队、阅读 Issue 第一楼 | 宽幅 Hero → 单行 Team → **单列文章 Feed** |
| 成员列表 | `/{owner}/{repo}/members` | 阅读完整公开成员资料、进入登记 | 标题/入口 → **桌面两列 / 手机一列**资料卡 |
| 成员登记 | `/{owner}/{repo}/members/register` | 以当前账号向展示分支登记成员 | 面包屑 → 操作者/分支说明 → **单列 640px 表单** |
| Issue 详情 | `/{owner}/{repo}/issues/{number}` | 阅读话题，参与讨论、查看劳动历史与属性 | 话题标题与正文 → **讨论 / 劳动历史 Tab** → 可按需展开的属性区 |
| Topic Page（公开聚合） | `/topic/{owner}/{repo}/` | 阅读活动/主题介绍并浏览该 Topic 公开项目 | **真实主办方海报优先横向主题卡** → 自适应项目封面卡片流 |

**重要差异：** Topic Page（#31）按指定公开 GitHub 仓库的 README、封面和 Topic 配置展示外部公开项目，**不核验 GitHub App Installation**，因此页面不得将搜索/白名单结果标为「已接入 LabourChain」。#3 要求 Installation 的平台级信息流继续独立跟踪。五页设计不合并两个数据契约。

## 2. 共用页面结构与视觉层次

**整体视觉基线**：采用 [视觉配色规范](./LabourChain-Visual-Style-Guide.md) 的 `canvas #11141B`、`surface #191E29`、`surface-raised #242B3B`、`primary-solid #5368E9`、`primary-link #92A6FF`、`signal-yellow #FBE13B`。亮黄仅少量辅助强调；正文、控件、错误信息保持可读。

- **页头：** 小型 LabourChain 身份标志、明确当前资源/返回路径、已有有效导航及登录状态。使用绳网式暗色窄条、胶囊式活动状态。示意图里的「项目 / 成员 / Issue」仅表示可到达的页面层级，不增加未经定义的全站快捷导航或当前页不存在的业务入口。
- **主体：** 内容框架、区块标题、分隔和暗色卡片，层级为页面标题 ＞ 页面主要内容 ＞ 卡片标题 ＞ 正文 ＞ 元信息。卡片可使用单角小切角/非对称圆角，作为原创样式特征；不复制游戏 UI 资产。
- **文章阅读：** Repo Feed / Issue 的标题优先，Markdown 内部 H1 不压过外部 Issue 标题；媒体、引用和代码在原文位置。链接与焦点使用亮蓝紫，状态文字不单凭颜色区分。
- **宽度候选：** 宽屏页面外框 `max-width ≈ 1120px`；Feed/Issue 长文阅读区 `max-width ≈ 760px`；成员页内容沿用既定约 `960px`；登记表单 `max-width ≈ 640px`。它们属于 D2 推荐参数，**未取得产品方逐项像素确认**。
- **节奏候选：** 桌面外边距 32px、平板 24px、手机 16px；区块间 28–36px、文章卡片间 16px、卡片内 20–24px（手机 16px），主要触达目标建议不小于 44px。
- **响应式：** 小屏约 320–599px 优先单列；600–899px 收缩内容分区；900px 以上可展开横向布局。以内容容纳能力为先，不将这些阈值冒称游戏官方断点；200% 缩放按实际可用视口折叠，页面整体不得横向溢出。
- **界面状态：** Loading、Empty、Error、Retry、Disabled、Focus、展开/收起及真实权限提示有可见文案和清晰位置；不展示不存在的统计数、游戏等级、点赞、封面、虚构团队身份或功能按钮。
- **浏览限制：** 当前稿为静态演示。没有获得任何真实 Vercel/生产环境屏幕验证，也没有真实 GitHub 写入验收。

## 3. 页面 A · 项目主页

### 3.1 桌面信息顺序

```text
┌──────────────────────────── 页面框架 ≤ 1120 ─────────────────────────────┐
│ LabourChain  /  项目身份与已有导航                                      │
├─────────────────────────────────────────────────────────────────────────┤
│ HERO · 项目名 + Description（有则优先） / 可用 README 摘要                 │
│       完整 README · GitHub 仓库入口                展示分支及操作          │
├─────────────────────────────────────────────────────────────────────────┤
│ TEAM · 一行头像 ○ ○ ○ ○ ○ →                        查看全部成员             │
├─────────────────────────────────────────────────────────────────────────┤
│ REPO FEED · 已存在的刷新 / 加载状态                                    │
│ ┌────────────────────────── 阅读栏 ≤ 760 ──────────────────────────┐    │
│ │ #编号 · Open/Closed · 作者 · 更新时间                             │    │
│ │ Issue 标题（高于正文 H1）                                          │    │
│ │ Markdown 正文预览 · 图片 / 视频外链 / 代码块                        │    │
│ │ 展开 / 收起                                                        │    │
│ │ 进入站内 Issue 详情 · GitHub 原文                                   │    │
│ └───────────────────────────────────────────────────────────────────┘    │
│ 下一条文章 · 无限下拉与可访问的手动加载后备                               │
└─────────────────────────────────────────────────────────────────────────┘
```

- Hero 保留紧凑文章介绍，Description 有值时只展示 Description；Description 缺失时提取可用 README 摘要，提供完整 README 的真实入口。
- Team 只显示单行头像，横向滚动；Hover/Focus/Tap 使用同一个非模态资料浮层，缺失头像遵循真实回退规则。
- Feed 继续展示**全部普通 Issues**（Open/Closed，排除 PR），依 `updated_at` 倒序；第一楼可展开预览，入口通往独立 Issue 页面，不加入看板、三列封面贴文、虚构投票/点赞。
- 设计强调：暗色 Hero、清晰 Team 区、带薄强调条的文章卡、元信息微胶囊；状态颜色始终配合文字。
- 手机视图：Hero 操作与分支独立换行；头像保持单行可横向滑动；文章卡占可用宽度，媒体随宽度缩放。

## 4. 页面 B · 成员列表

```text
页面标题「团队成员」           [添加成员／登录后添加成员（依权限）]
成员数量（仅来自真实 JSON 数据）
┌──────────────────────┐  ┌──────────────────────┐
│ ○  姓名 / 有值才显示角色│  │ ○ 姓名 / 有值才显示角色│
│ 完整纯文本介绍         │  │ 完整纯文本介绍         │
│ GitHub / 个人外链      │  │ GitHub / 个人外链      │
└──────────────────────┘  └──────────────────────┘
手机：卡片纵向单列
```

- 内容宽度沿用约 960px，宽屏双列，空间不足转单列，不引入成员搜索、角色排序或活跃榜。
- 卡片采用 `surface` 暗底、56px 头像、姓名、可选角色、完整 Bio 和实际存在的公开外链；按 `team-member.json` 的原始数组顺序。
- 空列表、文件缺失、JSON 格式异常、网络失败分别有明确反馈；添加入口必须服从 OAuth 和服务端仓库写权限，不默认所有访问者可提交。
- 卡片不捏造角色、介绍、项目数量或平台个人账户。

## 5. 页面 C · 成员登记

```text
项目 / 团队成员 / 添加成员
标题「添加团队成员」           表单阅读栏 ≤ 640
┌────────────────────────────────────────────────────┐
│ 当前已验证 GitHub 操作者 @login · 目标展示分支 main    │
├────────────────────────────────────────────────────┤
│ 显示名称 *                                            │
│ 项目角色（选填）                                       │
│ GitHub 用户名（选填）                                  │
│ 个人介绍（选填）                                       │
│ 头像 HTTPS URL（选填）  [就近错误反馈]                 │
│ 个人链接（最多三条，每条名称 + HTTPS URL）               │
│ [提交成员资料] [取消]                                 │
│ Bot Commit / PR / 错误、权限与待合并结果反馈             │
└────────────────────────────────────────────────────┘
```

- 单列视觉组织，不加入额外分支选择器、重复确认弹窗、图片上传或身份登记字段。
- 最先显示真实已验证操作者与**当前展示分支**，提示 Bot 提交语义；权限不足先显示说明，不伪造可提交状态。
- 表单基于既定字段和校验规则；`aria-invalid`、就近错误文字、首个错误字段焦点及错误持续反馈与实际输入同步。蓝紫主按钮配合明确 disabled/loading 状态。
- Commit 成功、PR 创建待合并、登录过期、写入失败均沿用已确认的独立反馈；不能把待合并 PR 当作成员已生效。示例 `main` 只作为可替换分支标签，不代表每个仓库都使用它。

## 6. 页面 D · Issue 详情

```text
项目 / Issue #number
┌──────────────────────────── 主要话题区域 ────────────────────────┐
│ Open/Closed + 编号 / 标题 / 作者、时间 / GitHub 来源                  │
│ 话题正文 Markdown（原文顺序；可能有真实成果摘要）                      │
│ [可按需展开的任务属性 / 左右辅助信息]                                │
├─────────────────────────────────────────────────────────────────┤
│  [讨论（默认）] [劳动历史]                                          │
│  评论顺序 / 真实劳动记录、输入反馈与失败恢复                         │
└─────────────────────────────────────────────────────────────────┘
```

- **独立 URL**、Back/Forward 和刷新仍成立；不会模仿同人弹层详情替换既有路由。
- 社区讨论优先，左/右侧栏默认隐藏、分别按需展开；宽屏可给辅助信息更多空间，手机收回为可访问的折叠区。
- 深色正文卡与蓝紫选中 Tab；原有讨论/劳动历史行为、输入权限和具体数据语义不变。
- 成果摘要、劳动小时数、记录或属性只显示真实可用数据；没有数据就呈真实空态，不将对话示意中的占位数值写成固定 UI 元素。

## 7. 页面 E · Topic Page（#31 独立公开聚合）

### 7.1 宽屏主版式

```text
/topic/{owner}/{repo}/
┌──────────────────────────── TOPIC HEAD 大卡片 ───────────────────────────┐
│ ┌────────── 主办方真实海报：视觉最大权重 ───────────┐ ┌───────────────┐ │
│ │                                                    │ │ README H1 标题│ │
│ │           cover.jpg 可用时展示                      │ │ H1 后正文介绍 │ │
│ │           缺失时不伪造图片                          │ │ 真实链接/内容 │ │
│ └────────────────────────────────────────────────────┘ │ email/datetime │ │
│                                                        └───────────────┘ │
└──────────────────────────────────────────────────────────────────────────┘
参与项目 · GitHub Topic 数据 / 加载与筛选结果
┌───────────────┐  ┌───────────────┐  ┌───────────────┐
│ 真实 Cover     │  │ 真实 Cover     │  │ 真实 Cover     │
│ Owner Avatar   │  │ Owner Avatar   │  │ Owner Avatar   │
│ 仓库名 / Title  │  │ 仓库名 / Title  │  │ 仓库名 / Title  │
│ 一行 Description│  │ 一行 Description│  │ 一行 Description│
└───────────────┘  └───────────────┘  └───────────────┘
更多 / 无项目 / 失败重试 / 搜索窗口耗尽
```

- **顶部主题卡**：沿用 #31 已确认的「布局 B：紧凑横卡、海报视觉优先」；只在 `cover.jpg` 实际存在时展示图像。README 首个 H1 作活动/主题标题，后续正文作介绍，`email`、`datetime` 等只在可读取时位于文字信息栏底部。内容由主办方自行在 README 中维护，不新增赛季/报名专用字段。
- **项目卡片**：采用绳网式图像上、身份/标题/一行描述下的信息层次，封面无可靠来源时显示可辨识的**原创无图占位层**，不虚构项目真实封面；Owner Avatar 使用真实来源/占位回退。
- **卡片容器**：Flex 自然换行，以卡片自身 `min-width/max-width/flex-basis` 决定列数；在宽屏示意中约三张一排，**不是固定三列或硬编码断点**。手机一般一列，可用宽度允许时自然过渡。
- **状态**：配置缺失/错误、Topic 搜索失败、白名单应用、过滤后继续补页、真实耗尽、GitHub Search 1000 窗口耗尽均以实际获取状态反馈；未满一屏不能自动判断搜索结束。匿名可以阅读。
- **项目资格**：#31 使用 `topics.config.yaml`（含 `topic`、默认 true 的 `whitelist`），白名单来自 `projects/*.yaml`；本页面不核查 Installation。项目卡片可以链接真实 GitHub 仓库，但不得标注为「已接入 LabourChain」。
- **错误反馈**：页面内显示阶段、可理解的错误、重试；登录用户的报告入口只在实际可用权限下展示。任何提交 GitHub Issue 的操作必须由真实用户显式确认，不在页面浏览时自动写入。
- **与 #3 分离**：#3 的平台已接入项目发现任务继续按其独立的 Installation 授权与公开展示判定 Review；这份 Topic Page 设计不会改变 #3 的实施门槛。

### 7.2 手机与中屏

- 手机：大主题横卡**纵向重排**，优先完整展示海报/封面，不以不可读的窄栏挤压 README 内容；活动标题、介绍和页脚信息随后排列。
- 中屏：海报与文字可按内容宽度决定横排或纵排；项目卡自身收缩后自然换行，不出现整页水平滚动。
- 长标题与长仓库名可换行或截断但保留来源入口；描述仅一行，完整项目资料通过可访问链接查看。
- 不以固定封面占比剪掉主办方海报中的关键信息；若图片比例复杂，优先 `contain` 与清晰边界，最终效果由用户真实视觉审阅。
