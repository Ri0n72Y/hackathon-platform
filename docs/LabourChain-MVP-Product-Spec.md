# LabourChain Board：MVP 产品说明

-   **文档状态：** Draft 0.1
-   **产品形态：** 部署在 Vercel 上的网页服务
-   **首批用户：** 黑客松比赛团队
-   **首个数据源：** 公开 GitHub 仓库
-   **核心原则：** 以 GitHub Issue 作为任务与讨论载体；用配置化 Label
    驱动看板和频道；为后续劳动链集成预留数据模型，但第一版不运行完整劳动链协议。

## 1. 产品目标

本产品为 GitHub
仓库提供仓库级看板和更适合社区参与的界面。它将项目发现、Issue
看板、频道讨论和基础劳动记录放在同一产品中。

第一版重点验证：

1.  黑客松团队能否快速挂载仓库并开始使用看板。
2.  以 GitHub Label 驱动状态，是否能同时兼容 GitHub 原生工作流。
3.  将频道表示为 Issue，是否能以较低的实现成本支持社区讨论。
4.  Commit 与结构化 Issue 评论能否形成可追溯的基础劳动记录。
5.  不依赖在线业务数据库，能否通过浏览器读取、缓存和渲染公开仓库数据。

## 2. 第一版范围

### 2.1 包含

-   前端采用 Cordis 作为应用的模块与插件组织基础；具体 UI 与构建方案由技术调研确认。
-   GitHub App 用户授权。
-   公开 GitHub 仓库挂载。
-   公共项目索引仓库驱动的首页项目发现。
-   读取 `labourchain.config.yaml`。
-   读取和展示 GitHub Issue；第一版不获取 PR。
-   基于 `status:*` Label 的看板。
-   基于 `channel:*` Label 的频道页面。
-   创建 Issue、回复评论和修改状态 Label。
-   配置初始化与变更时的 Label 同步。
-   浏览器临时缓存、普通刷新和强制刷新。
-   基础劳动记录展示。
-   可选的 `team-index/` 成员目录。

### 2.2 不包含

-   私有 GitHub 仓库。
-   PR 获取或 PR 看板。
-   GitLab、Gitea、Forgejo 等其他平台适配器。
-   GitHub Webhook 驱动的持续后台同步、队列和定时对账。
-   在线业务数据库及服务端共享缓存。
-   完整劳动链协议执行，包括签名、打包、验证和链式查询。
-   劳动价值计算、贡献排名或声誉系统。
-   细粒度权限、私有频道和复杂社区治理。
-   独立的频道主题/Thread 数据模型。
-   完整的成员电子简历系统。
-   完整的异常数据诊断界面。无效数据诊断默认只面向有权限的仓库维护者，界面可后置。

## 3. 用户与权限

### 3.1 仓库挂载

-   只有仓库 Owner 或具有相应维护权限的 Maintainer 可以挂载仓库。
-   第一版只支持公开仓库。
-   用户通过 GitHub App 用户授权流程登录和授权。
-   写操作使用用户授权令牌，并遵守 GitHub 用户本身的权限。
-   GitHub App 私钥和其他服务端凭据不得放在前端。

### 3.2 普通操作

除仓库本身的权限或设置限制外，任何具有相应 GitHub
权限的已授权账号都可以创建
Issue、回复评论和修改任务状态。第一版不增加独立的细粒度角色系统。

匿名用户可以浏览公开项目；需要写入 GitHub 的操作必须经过用户授权。

## 4. 首页与项目页面

### 4.1 首页项目发现

-   首页读取一个部署配置指定的公共索引仓库。
-   索引仓库维护项目清单及展示所需的少量元数据。
-   前端在浏览器中读取索引并渲染项目卡片。
-   项目卡片可展示项目名称、简介、近期进展和参与入口。
-   第一版以索引仓库为主要发现来源；GitHub Topics 可作为后续扩展。
-   新项目是否出现在首页，取决于索引仓库是否收录该项目。

### 4.2 项目详情页

项目详情页直接从对应的公开 GitHub 仓库读取配置、Issue
和所需的劳动记录来源数据。页面包含：

-   **概览：** 项目简介与参与入口。
-   **看板：** 按状态展示 Issue 卡片。
-   **频道：** 按配置展示频道 Issue 及其评论。
-   **劳动记录：** 展示从结构化 Issue 评论和 Commit Message
    解析出的记录。
-   **成员：** 展示可用的团队成员信息。

看板与频道是独立的路由维度。如果一个 Issue
同时满足看板和频道规则，它可以出现在两个视图中。

## 5. 配置文件

### 5.1 文件名与职责

仓库根目录使用单一配置文件：

`labourchain.config.yaml`

配置文件定义有效的状态标签、频道标签、显示方式，以及需要由本产品管理的命名空间。前端解析配置并生成界面；服务端
Function 在写入或同步前必须重新校验配置和操作权限。

具体字段可以在实现时进一步细化，但必须保持以下语义。

### 5.2 命名空间规则

-   `status:*`：定义看板状态。
-   `channel:*`：定义频道。
-   其他命名空间只有在配置中明确声明后，才由本产品管理。
-   标签匹配使用完整的命名空间前缀，例如 `foo:`，不得把 `foo:` 与
    `foobar:` 混为一谈。

### 5.3 命名空间的三种配置状态

1.  **命名空间不存在：** 本产品不管理该命名空间，不检查、不修改。
2.  **命名空间存在且标签列表非空：**
    本产品管理该命名空间；配置中列出的标签是有效值。
3.  **命名空间存在但标签列表为空：**
    本产品仍管理该命名空间，但没有有效标签值；同步时移除 Issue
    上该命名空间的所有标签。

例如，保留 `foo: []` 表示清空所有 Issue 上的 `foo:*` 标签。直接删除
`foo` 配置段落则表示停止管理该命名空间，不执行清理。

### 5.4 默认状态

状态值由配置定义，不写死在程序中。默认配置可包含：

-   `status:todo`
-   `status:doing`
-   `status:review`
-   `status:done`
-   `status:archived`

`status:archived`
表示归档列表，不是普通看板列。它默认隐藏，用户可手动打开归档列表。

### 5.5 默认频道

默认配置提供 `channel:wishlist`，并为它指定 Wishlist
专用的前端展示方式。用户删除该频道配置后，前端不再渲染 Wishlist
专用页面。

Wishlist 在数据结构上没有特殊对象：它仍然是一个频道
Issue，评论就是该频道的讨论内容。

## 6. GitHub Label 初始化与同步

### 6.1 初始化

首次挂载仓库或配置变更时，由 Vercel Function 执行同步：

1.  读取当前配置和 GitHub 仓库状态。
2.  校验配置格式、用户权限和受管命名空间。
3.  为配置中缺少的 Label 定义创建 GitHub Label。
4.  检查 Issue 上的受管标签。
5.  移除不在当前配置有效值中的受管标签。
6.  返回同步结果和失败信息。

### 6.2 清理边界

-   只管理配置中明确声明的命名空间。
-   只清理 Issue 上的标签；第一版不获取或主动修改 PR。
-   不删除仓库级 Label 定义。需要删除 Label 定义时，由维护者在 GitHub
    中手动操作。
-   在 GitHub 删除仓库级 Label 定义后，GitHub 会自动从相关 Issue 和 PR
    上移除该标签。
-   如果配置中移除整个命名空间，则停止管理该命名空间，不自动清理。
-   如果配置保留命名空间但将其标签列表设为空，则清理该命名空间在 Issue
    上的所有标签。

配置同步包含多个 GitHub API
操作，不是原子事务。部分操作失败时，必须报告失败；允许安全重试，不得修改未声明为受管的标签。

## 7. 看板规则

### 7.1 Issue 获取

-   第一版只获取 Issue，不获取 PR。
-   默认获取 Open Issue。
-   Closed Issue 默认不显示。
-   用户开启"显示已关闭"后，再分页获取 Closed Issue。
-   看板不要求一次性获取全部历史 Issue。

### 7.2 状态解析

-   Issue 必须具有且仅具有一个有效的 `status:*`
    标签，才可作为普通看板卡片渲染。
-   没有状态标签、存在多个状态标签，或状态标签未在当前配置中定义的
    Issue，不渲染。
-   无效数据可提供诊断信息；第一版诊断界面不是阻塞功能。
-   `Open/Closed` 是 GitHub 生命周期状态，与 `status:*` 标签分开处理。
-   `status:archived` 对应独立归档列表，默认隐藏。
-   移动卡片时，只修改 `status` 命名空间内的标签，不修改其他标签。

### 7.3 交互

-   复用现有 Board 的拖拽（DnD）、样式和卡片交互设计。
-   点击卡片后直接展示对应 Issue，可使用侧边栏。
-   搜索、筛选、排序及列显示偏好保存在本地。
-   支持创建 Issue、回复评论和修改状态。
-   如果 GitHub
    写入失败，界面不得永久显示未成功的变更；必须显示失败并允许恢复或重试。

## 8. 频道规则

-   每个频道由一个有效的 Open Issue 表示。
-   有效频道 Issue 必须恰好具有一个有效 `channel:*`
    标签，且该标签存在于当前配置中。
-   同一频道有多个候选 Issue 时，选择创建时间最新的有效 Issue。
-   如果频道没有有效 Issue，显示空状态。
-   一个 Issue 如果具有多个 `channel:*`
    标签，则频道归属无效，不在频道页面渲染。
-   频道讨论使用对应 Issue 的评论，不另建 Thread 数据模型。
-   Wishlist
    使用与其他频道相同的有效性和选择规则；其特殊性仅来自默认配置和前端展示方式。
-   不同频道的创建和接入交互可以后续再设计。

## 9. 领域数据模型

### 9.1 Repo

`Repo` 是产品的仓库级根对象。第一版只实现 GitHub
类型，但领域模型不得将所有对象的身份都绑定到 GitHub 特有字段。未来
GitHub 仓库可以成为劳动链仓库体系中的一种特殊类型。

### 9.2 CardItem

`CardItem` 是标准任务卡片，直接引用来源 Issue，不建立完整 Issue
快照。可以预留 `patch?: Partial<CardItem>`
用于少量冗余字段，但第一版不实现完整 Patch 系统。

GitHub 管理的字段不能被本地 Patch 静默覆盖。

### 9.3 Asset

Asset 表示实际存在的文件或资产。Git 管理的仓库中，Asset 可以通过 Commit
SHA 定位；没有 Git 版本管理时，Asset 可以指向具体文件。

第一版至少支持 GitHub Commit Asset，并保留仓库、Commit
SHA、原始地址、作者、提交者、提交时间和原始提交信息等必要来源信息。

### 9.4 Labour Record

劳动记录有两个主要来源：

1.  Commit Message。
2.  Issue 中符合约定格式的结构化评论。

结构化评论以 Issue 回复中的独立 `yaml` 代码块表示，一条有效评论对应一条劳动记录。
`labour` 是顶层标识，字段契约如下：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `work` | 是 | 用自然语言描述具体做了什么，允许多行文本。 |
| `commits` | 否 | 关联的 GitHub Commit SHA 列表；测试、写作、与 AI 交流等工作可以没有 Commit。 |
| `outcome` | 否 | 劳动成果说明；可以补充 Commit，也可以独立说明没有 Commit 的成果。 |
| `duration` | 是 | 主观估计时长，按 0.5 小时为单位，以 `~1.5h` 等字符串表达；不要求计时证明。 |
| `start-end` | 否 | 劳动起止时间；如填写，使用 `start` 与 `end` 两个 RFC 3339 时间戳。 |

最短记录：

```yaml
labour:
  work: 测试 GitHub App 授权流程
  duration: ~1.5h
```

带成果、Commit 和起止时间的记录：

```yaml
labour:
  work: |
    测试 GitHub App 用户授权，并整理使用文档。
  commits:
    - 6dcb09b5b57875f334f61aebed695e2e4193db5e
  outcome: |
    验证了授权回调，并整理出配置说明。
  duration: ~2h
  start-end:
    start: "2026-10-22T09:00:00Z"
    end: "2026-10-22T11:00:00Z"
```

`duration` 以小时计，接受 `~0.5h`、`~1h`、`~1.5h` 等 0.5 小时递增的**主观估计**，不根据 Commit 数量或起止时间自动推算；`start-end` 完全可选，不填时劳动实际发生时间保持未知。GitHub 评论的创建时间只作为提交时间，不代替劳动发生时间。无 Commit 的劳动记录同样有效。

评论的 GitHub ID、作者、创建时间和所属 Issue 使用 GitHub 原始元数据，不要求劳动者重复填写。仅识别顶层为 `labour` 的完整 YAML 代码块；未通过校验的评论保留为普通讨论。关联多个 Commit SHA 时，一条结构化劳动记录与多个 Commit Asset 按一对多关系处理。

规则：

-   有效结构化评论作为劳动记录展示，不再作为普通评论渲染。
-   如果一个 Commit 已被结构化劳动记录包含，不再额外生成独立的 Commit
    Message 劳动记录。
-   没有被结构化记录包含的 Commit，可以生成不完整的基础劳动记录，只包含
    Commit 默认时间和单薄的 Message；不假设有估时或其他字段。
-   无法通过格式校验的评论仍作为普通评论显示。
-   原始 Issue 评论和 Commit 来源仍然可追溯。
-   第一版不计算劳动价值，也不运行完整劳动链协议。

同一 Commit
被多个结构化记录引用时，第一版不自动合并；应将冲突作为无效或待处理数据，避免重复展示。

## 10. 团队成员索引

仓库可以提供 `team-index/` 目录，每位成员一个 Markdown 文件，并由一个总
`index` 文件建立索引。

MVP 只需要极简成员信息，允许登记开发者、Lead、运营、设计、文档维护者和
Bot 等参与主体。成员可以没有 GitHub 账号。

具体字段契约暂不在本说明中固定。后续将结合劳动记录扩展为可追溯的电子简历。

## 11. 缓存与刷新

-   第一版不使用在线业务数据库。
-   仓库数据由用户浏览器按需读取、临时缓存和渲染。
-   UI 偏好和筛选器状态保存在本地。
-   支持普通刷新与强制刷新。
-   普通刷新可使用有效缓存并按需检查更新。
-   强制刷新重新获取对应数据。
-   请求失败时，可以显示已有缓存，但必须提示数据可能过期。
-   应使用分页和请求合并减少 GitHub API 调用，并处理 API 速率限制。
-   不实现 Webhook 持续同步、后台队列和定时对账。

访问令牌不得作为普通数据写入
`localStorage`。授权会话与令牌存储方案在技术设计阶段确定。

## 12. 部署与技术边界

-   前端采用 Cordis 组织应用模块、服务和插件；浏览器运行方式、UI 框架及构建集成需通过技术调研验证（见 Issue #1）。
-   前端部署在 Vercel。
-   Vercel Functions 用于 GitHub App 授权流程、仓库挂载、GitHub
    写操作和配置同步。
-   配置解析、命名空间解析、状态过滤和频道选择等领域逻辑尽量使用纯
    TypeScript 模块，以便测试和复用。
-   第一版不部署常驻云
    Worker；如果实际测试证明托管函数不能满足需求，再单独评估。
-   不因预留多平台能力而提前实现其他 Git 适配器。

## 13. MVP 验收标准

-   [ ] 仓库 Owner / Maintainer 能授权并挂载公开 GitHub 仓库。
-   [ ] 首页能从配置好的公共索引仓库读取项目清单并渲染项目卡片。
-   [ ] 项目页面能读取并校验 `labourchain.config.yaml`。
-   [ ] 配置中缺少的 Label 定义能被创建。
-   [ ] 配置中声明的受管命名空间能正确清理 Issue 上的无效标签。
-   [ ] 未声明的命名空间不会被修改。
-   [ ] 空命名空间列表会清理对应 Issue
    标签；删除整个配置段落则停止管理。
-   [ ] 仓库级 Label 定义不会被本产品自动删除。
-   [ ] 看板只获取 Issue，不获取 PR。
-   [ ] 只有具有唯一有效状态标签的 Issue 才渲染为卡片。
-   [ ] Closed Issue 默认隐藏，打开开关后可以分页查看。
-   [ ] `status:archived` 显示为默认隐藏的归档列表。
-   [ ] 频道只选择最新创建的有效 Open Issue。
-   [ ] 删除 Wishlist 配置后，Wishlist 专用页面不再渲染。
-   [ ] 创建 Issue、回复评论和修改 Label 时遵守 GitHub 用户权限。
-   [ ] 按 `labour` YAML 格式解析 Issue 评论，支持必填 `work` 和
    以 0.5 小时为单位的主观估时 `duration`，以及可选 `commits`、
    `outcome`、`start-end`；无 Commit 的记录仍有效。
-   [ ] 结构化劳动记录能关联多个 Commit，且被包含的 Commit
    不重复生成基础记录。
-   [ ] 浏览器刷新和强制刷新行为清楚；缓存失败不会被伪装成最新数据。
-   [ ] GitHub API 或配置同步失败时，用户能看到失败状态，并可以重试。

## 14. 实现阶段再确定的细节

以下内容不阻止当前 MVP
边界成立，但需要在实现前或实现过程中形成具体契约：

-   `labourchain.config.yaml` 的最终字段名和完整 Schema。
-   结构化劳动记录 YAML 的解析实现与错误提示（字段格式见 §9.4）。
-   `team-index/` 的最小字段和索引格式。
-   首页索引仓库的具体文件布局与项目元数据字段。
-   GitHub App 用户令牌的会话与安全存储方案。
-   Cordis 与具体前端 UI、构建流程及 Vercel 部署的集成方案（见 Issue #1）。
-   Commit 的发现、分页和增量读取策略。
-   配置同步部分失败时的重试和结果呈现细节。
-   频道创建和初始化的交互形态。

这些细节应在不扩大 MVP 范围的前提下确定。
