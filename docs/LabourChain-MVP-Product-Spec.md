# LabourChain Board：MVP 产品说明

-   **文档状态：** Draft 0.1
-   **产品形态：** 部署在 Vercel 上的网页服务
-   **首批用户：** 黑客松比赛团队
-   **首个数据源：** 公开 GitHub 仓库
-   **核心原则：** 优先使用 GitHub 原生能力和现有仓库数据。以 GitHub Issue/评论承载讨论，以 Label 驱动频道及后续看板；MVP 不建立需要独立维护的全局项目索引、注册表或跨仓库聚合数据。为后续劳动链集成预留数据模型，但第一版不运行完整劳动链协议。

## 1. 产品目标

本产品为公开 GitHub 仓库提供更适合社区参与的项目页面，呈现项目介绍、团队成员、Issue 正文动态、频道讨论和基础劳动记录。项目发现优先使用 GitHub Topic / Repository Search 等现有能力；若某项发现或聚合功能必须依赖额外维护的全局数据，则不纳入 MVP。看板保留为独立页面，后置实现；第一版项目主页不展示看板。

第一版重点验证：

0. **原则：** 优先围绕 GitHub 能直接承担、并且能以现有数据实现的功能设计 MVP。公开 GitHub 仓库是主要数据源；不额外维护全局项目索引、注册表或跨仓库聚合数据。若功能必须依赖这类自建全局数据，则从 MVP 移除或后置。
1. 黑客松团队能否快速挂载公开仓库，并通过项目主页了解项目、成员与近期动态。
2. 能否使用 GitHub Topic / Repository Search 等原生能力发现项目，而不维护独立全局项目清单；平台授权状态若不能从 GitHub App 相关数据可靠确认，则将相应筛选或信息流后置。
3. 能否以 GitHub Issue 和评论承载频道讨论及项目动态，降低社区参与成本。
4. Commit 与结构化 Issue 评论能否形成可追溯的基础劳动记录。
5. 不依赖在线业务数据库，能否通过浏览器读取、缓存和渲染公开仓库数据。

## 2. 第一版范围

### 2.1 包含

-   前端采用 Cordis 作为应用的模块与插件组织基础；具体 UI 与构建方案由技术调研确认。
-   GitHub App 用户授权。
-   公开 GitHub 仓库挂载。
-   基于 GitHub Topic / Repository Search 的项目发现；不建立独立全局项目索引。若平台授权仓库过滤无法仅依靠 GitHub App / GitHub API 的权威数据可靠实现，则该过滤或信息流后置。
-   读取 `labourchain.config.yaml`。
-   读取和展示 GitHub Issue；第一版不获取 PR。
-   基于 `channel:*` Label 的频道页面。
-   创建 Issue、回复评论和修改状态 Label。
-   配置初始化与变更时的 Label 同步。
-   浏览器临时缓存、普通刷新和强制刷新。
-   基础劳动记录展示。
-   从仓库根目录的 `team-member.json` 读取团队成员信息，并在成员头像悬停时展示详细信息；允许项目参与者手动维护，也允许平台通过 GitHub App Bot 身份提交修改。
-   项目主页 Repo 动态读取所展示 GitHub Issue 的第一楼（Issue body），按 Markdown 和平台支持的扩展格式（包括视频外链）渲染。

### 2.2 不包含

-   第一版项目主页内的看板预览，以及第一版交付中的独立 Kanban 页面。看板保留为独立页面，后置实现，不与项目主页合并。
-   私有 GitHub 仓库。
-   PR 获取或 PR 看板。
-   GitLab、Gitea、Forgejo 等其他平台适配器。
-   GitHub Webhook 驱动的持续后台同步、队列和定时对账。
-   在线业务数据库及服务端共享缓存。
-   完整劳动链协议执行，包括签名、打包、验证和链式查询。
-   劳动价值计算、贡献排名或声誉系统。
-   细粒度权限、私有频道和复杂社区治理。
-   独立的频道主题/Thread 数据模型。
-   完整的成员电子简历系统。
-   完整的异常数据诊断界面。无效数据诊断默认只面向有权限的仓库维护者，界面可后置。

## 3. 用户与权限

### 3.1 仓库挂载与接入判定

-   只有仓库 Owner 或具有相应维护权限的 Maintainer 可以安装/授权 GitHub App，并授予目标公开仓库访问范围。
-   第一版只支持公开仓库。
-   **平台接入状态完全由 GitHub 当前的 App Installation 关系决定**：目标仓库必须属于某个获准 Installation 的仓库范围。不设平台内第二次绑定，也不建立全局仓库登记表。
-   用户 OAuth 登录/授权用于识别具体用户，并按用户授权链路读取/同步数据或执行交互式写入；OAuth 可见性本身不决定仓库是否接入平台。
-   写操作使用用户授权令牌，并遵守 GitHub 用户本身的权限。
-   GitHub App 私钥和其他服务端凭据不得放在前端。

### 3.2 普通操作

除仓库本身的权限或设置限制外，任何具有相应 GitHub
权限的已授权账号都可以创建
Issue、回复评论和修改任务状态。第一版不增加独立的细粒度角色系统。

匿名用户可以浏览公开项目；需要写入 GitHub 的操作必须经过用户授权。

## 4. 首页与项目页面

### 4.1 首页项目发现

-   使用 GitHub Topic / Repository Search 等原生能力查询候选公开仓库，不维护额外的全局项目索引或项目注册表。
-   项目卡片可展示项目名称、简介、近期进展和参与入口；信息应来自对应的 GitHub 仓库及其公开数据。
-   如果主题信息流必须限制为已接入平台的仓库，应依据 GitHub 当前 App Installation 关系及其获准仓库范围验证目标仓库；当前浏览者的 OAuth 可见性或 Topic 命中不能替代接入判定。
-   如果无法在不维护独立全局登记数据的前提下可靠完成授权过滤，则将该过滤或相关信息流后置，不以自建全局数据表补足。

### 4.2 项目详情页

项目详情页直接从对应的公开 GitHub 仓库读取配置、Issue 和所需的劳动记录来源数据。第一版项目主页不展示看板；看板将作为独立页面在后续阶段实现。页面包含：

-   **概览：** 项目简介与参与入口。
-   **频道：** 按配置展示频道 Issue 及其评论。
-   **劳动记录：** 展示从结构化 Issue 评论和 Commit Message
    解析出的记录。
-   **团队成员：** 从仓库根目录的 `team-member.json` 读取成员信息，项目成员头像悬停时展示详细信息。文件可由参与者手动维护；通过平台编辑时，由 GitHub App Bot 身份向对应 Repo 提交文件变更，服务端必须校验发起人的仓库写入权限。
-   **Repo 动态：** 读取动态列表中所展示 GitHub Issue 的第一楼（Issue body），将正文作为 Markdown 文档渲染，并支持平台扩展格式，包括视频外链。评论仍作为 Issue 讨论内容，不替代第一楼正文。

后续实现的独立看板与频道是不同的路由维度。如果一个 Issue 同时满足看板和频道规则，它可以在看板页面和频道页面中分别出现；此规则不代表第一版已经提供看板。

## 5. 配置文件

### 5.1 文件名与职责

仓库根目录使用单一配置文件：

`labourchain.config.yaml`

配置文件定义有效的状态标签、频道标签、显示方式，以及需要由本产品管理的命名空间。前端解析配置并生成界面；服务端
Function 在写入或同步前必须重新校验配置和操作权限。

具体字段可以在实现时进一步细化，但必须保持以下语义。

### 5.2 命名空间规则

-   `status:*`：表达 Issue 的整体状态；`status:archived` 另有独立于当前看板分列 Namespace 的归档规则。
-   `channel:*`：定义频道。
-   后续看板可以选择配置中已声明且具有有效标签的任一 Namespace 分列；`status:*` 不是唯一的分列来源。
-   其他命名空间只有在配置中明确声明后，才由本产品管理。
-   标签匹配使用完整的命名空间前缀，例如 `foo:`，不得把 `foo:` 与
    `foobar:` 混为一谈。

### 5.3 命名空间的三种配置状态

1.  **命名空间不存在：** 本产品不管理该命名空间，不检查、不修改。
2.  **命名空间存在且标签列表非空：**
    本产品管理该命名空间；配置中列出的标签是有效值。
3.  **命名空间存在但标签列表为空：**
    本产品仍管理该命名空间，但没有有效标签值；同步时移除 Issue
    上该命名空间的所有标签。

例如，保留 `foo: []` 表示清空所有 Issue 上的 `foo:*` 标签。直接删除
`foo` 配置段落则表示停止管理该命名空间，不执行清理。

### 5.4 默认状态

状态值由配置定义，不写死在程序中。默认配置可包含：

-   `status:todo`
-   `status:doing`
-   `status:review`
-   `status:done`
-   `status:archived`

`status:archived`
表示归档列表，不是普通看板列。它默认隐藏，用户可手动打开归档列表。

### 5.5 默认频道

默认配置提供 `channel:wishlist`，并为它指定 Wishlist
专用的前端展示方式。用户删除该频道配置后，前端不再渲染 Wishlist
专用页面。

Wishlist 在数据结构上没有特殊对象：它仍然是一个频道
Issue，评论就是该频道的讨论内容。

## 6. GitHub Label 初始化与同步

### 6.1 初始化

首次挂载仓库或配置变更时，由 Vercel Function 执行同步：

1.  读取当前配置和 GitHub 仓库状态。
2.  校验配置格式、用户权限和受管命名空间。
3.  为配置中缺少的 Label 定义创建 GitHub Label。
4.  检查 Issue 上的受管标签。
5.  移除不在当前配置有效值中的受管标签。
6.  返回同步结果和失败信息。

### 6.2 清理边界

-   只管理配置中明确声明的命名空间。
-   只清理 Issue 上的标签；第一版不获取或主动修改 PR。
-   不删除仓库级 Label 定义。需要删除 Label 定义时，由维护者在 GitHub
    中手动操作。
-   在 GitHub 删除仓库级 Label 定义后，GitHub 会自动从相关 Issue 和 PR
    上移除该标签。
-   如果配置中移除整个命名空间，则停止管理该命名空间，不自动清理。
-   如果配置保留命名空间但将其标签列表设为空，则清理该命名空间在 Issue
    上的所有标签。

配置同步包含多个 GitHub API
操作，不是原子事务。部分操作失败时，必须报告失败；允许安全重试，不得修改未声明为受管的标签。

## 7. 看板规则（后续独立页面实现时适用）

本节保留看板的数据与交互约束供后续实现使用；看板不属于第一版项目主页，也不属于第一版交付范围。

### 7.1 Issue 获取

-   第一版只获取 Issue，不获取 PR。
-   默认获取 Open Issue。
-   Closed Issue 默认不显示。
-   用户开启"显示已关闭"后，再分页获取 Closed Issue。
-   看板不要求一次性获取全部历史 Issue。

### 7.2 分列与状态解析

-   看板可选择 `labourchain.config.yaml` 中已声明且有效标签列表非空的任一 Namespace 作为当前分列依据；`status:*` 不是唯一的分列来源。
-   当前分列 Namespace 中，只有配置明确列出的标签值才有效。配置内标签顺序从小到大；Issue 在该 Namespace 中有多个有效标签时，归入配置顺序中最大的有效标签所在列。没有有效标签的 Issue 不归入该 Namespace 的普通列。
-   只要 Issue 含有 `status:archived`，无论当前看板选择哪个 Namespace，默认都隐藏；用户在 Filter 中明确选择「包含 archived」后才纳入候选结果。`status:archived` 不是普通看板列。此规则与 GitHub 的 Open/Closed 生命周期状态分开处理。
-   `pinned` 只影响所属列内的置顶顺序，不决定分列 Namespace 或列归属。
-   无效数据可提供诊断信息；第一版诊断界面不是阻塞功能。
-   跨列拖动时，只移除当前来源列对应的受管标签，再添加目标列标签；操作只针对当前选定的 Namespace，保留同一 Namespace 的其他标签及其他 Namespace 的标签。若 Issue 仍有更大的有效标签，按上述规则重新读取后可能归入更大的标签列；不得为避免此结果而暗中删除其他标签。
-   同列手动排序只改变当前页面的临时顺序，不写入 GitHub；执行手动排序时清空 Filter。刷新或重新应用筛选/排序后，临时顺序重置。
### 7.3 交互

-   复用现有 Board 的拖拽（DnD）、样式和卡片交互设计。
-   点击卡片后直接展示对应 Issue，可使用侧边栏。
-   看板的 Namespace、Filter 等可分享视图条件由 URL 保存；同列手动排序仅在当前页面临时生效，不写入 GitHub，并会清空 Filter。刷新或重新应用筛选/排序后，临时顺序重置。
-   支持创建 Issue、回复评论和修改状态。
-   如果 GitHub
    写入失败，界面不得永久显示未成功的变更；必须显示失败并允许恢复或重试。

## 8. 频道规则

-   每个频道由一个有效的 Open Issue 表示。
-   有效频道 Issue 必须恰好具有一个有效 `channel:*`
    标签，且该标签存在于当前配置中。
-   同一频道有多个候选 Issue 时，选择创建时间最新的有效 Issue。
-   如果频道没有有效 Issue，显示空状态。
-   一个 Issue 如果具有多个 `channel:*`
    标签，则频道归属无效，不在频道页面渲染。
-   频道讨论使用对应 Issue 的评论，不另建 Thread 数据模型。
-   Wishlist
    使用与其他频道相同的有效性和选择规则；其特殊性仅来自默认配置和前端展示方式。
-   不同频道的创建和接入交互可以后续再设计。

## 9. 领域数据模型

### 9.1 Repo

`Repo` 是产品的仓库级根对象。第一版只实现 GitHub
类型，但领域模型不得将所有对象的身份都绑定到 GitHub 特有字段。未来
GitHub 仓库可以成为劳动链仓库体系中的一种特殊类型。

### 9.2 CardItem

`CardItem` 是标准任务卡片，直接引用来源 Issue，不建立完整 Issue
快照。可以预留 `patch?: Partial<CardItem>`
用于少量冗余字段，但第一版不实现完整 Patch 系统。

GitHub 管理的字段不能被本地 Patch 静默覆盖。

### 9.3 Asset

Asset 表示实际存在的文件或资产。Git 管理的仓库中，Asset 可以通过 Commit
SHA 定位；没有 Git 版本管理时，Asset 可以指向具体文件。

第一版至少支持 GitHub Commit Asset，并保留仓库、Commit
SHA、原始地址、作者、提交者、提交时间和原始提交信息等必要来源信息。

### 9.4 Labour Record

劳动记录有两个主要来源：

1.  Commit Message。
2.  Issue 中符合约定格式的结构化评论。

结构化评论以 Issue 回复中的独立 `yaml` 代码块表示，一条有效评论对应一条劳动记录。
`labour` 是顶层标识，字段契约如下：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `work` | 是 | 用自然语言描述具体做了什么，允许多行文本。 |
| `commits` | 否 | 关联的 GitHub Commit SHA 列表；测试、写作、与 AI 交流等工作可以没有 Commit。 |
| `outcome` | 否 | 劳动成果说明；可以补充 Commit，也可以独立说明没有 Commit 的成果。 |
| `hr` | 是 | 主观估计时长，按 0.5 小时为单位，以 `~1.5h` 等字符串表达；不要求计时证明。 |
| `start-end` | 否 | 劳动起止时间；如填写，使用 `start` 与 `end` 两个 RFC 3339 时间戳。 |

最短记录：

```yaml
labour:
  work: 测试 GitHub App 授权流程
  hr: ~1.5h
```

带成果、Commit 和起止时间的记录：

```yaml
labour:
  work: |
    测试 GitHub App 用户授权，并整理使用文档。
  commits:
    - 6dcb09b5b57875f334f61aebed695e2e4193db5e
  outcome: |
    验证了授权回调，并整理出配置说明。
  hr: ~2h
  start-end:
    start: "2026-10-22T09:00:00Z"
    end: "2026-10-22T11:00:00Z"
```

`hr` 以小时计，接受 `~0.5h`、`~1h`、`~1.5h` 等 0.5 小时递增的**主观估计**，不根据 Commit 数量或起止时间自动推算；`start-end` 完全可选，不填时劳动实际发生时间保持未知。GitHub 评论的创建时间只作为提交时间，不代替劳动发生时间。无 Commit 的劳动记录同样有效。

评论的 GitHub ID、作者、创建时间和所属 Issue 使用 GitHub 原始元数据，不要求劳动者重复填写。仅识别顶层为 `labour` 的完整 YAML 代码块；未通过校验的评论保留为普通讨论。关联多个 Commit SHA 时，一条结构化劳动记录与多个 Commit Asset 按一对多关系处理。

规则：

-   有效结构化评论作为劳动记录展示，不再作为普通评论渲染。
-   如果一个 Commit 已被结构化劳动记录包含，不再额外生成独立的 Commit
    Message 劳动记录。
-   没有被结构化记录包含的 Commit，可以生成不完整的基础劳动记录，只包含
    Commit 默认时间和单薄的 Message；不假设有估时或其他字段。
-   无法通过格式校验的评论仍作为普通评论显示。
-   原始 Issue 评论和 Commit 来源仍然可追溯。
-   第一版不计算劳动价值，也不运行完整劳动链协议。

同一 Commit
被多个结构化记录引用时，第一版不自动合并；应将冲突作为无效或待处理数据，避免重复展示。

## 10. 团队成员文件

仓库根目录可以提供 `team-member.json`，作为该 Repo 团队成员信息的权威来源。

- 项目参与者可以直接在自己的 Repo 中手动维护此文件。
- 平台读取该文件，并在成员头像悬停时展示对应成员的详细信息。
- 如果用户通过平台编辑成员信息，平台通过 GitHub App **Bot 身份**将文件变更提交到对应 Repo；服务端在写入前校验发起人对该仓库的写入权限。
- 文件字段、成员标识、头像来源、缺失/无效数据处理方式尚未冻结，应在实现前定义最小 JSON Schema，并确保手动提交与平台写入产生同样可读取的格式。
- 该文件不构成独立账号系统，也不代表额外的 GitHub 权限授予。

## 11. 缓存与刷新

-   第一版不使用在线业务数据库。
-   仓库数据由用户浏览器按需读取、临时缓存和渲染。
-   UI 偏好和筛选器状态保存在本地。
-   支持普通刷新与强制刷新。
-   普通刷新可使用有效缓存并按需检查更新。
-   强制刷新重新获取对应数据。
-   请求失败时，可以显示已有缓存，但必须提示数据可能过期。
-   应使用分页和请求合并减少 GitHub API 调用，并处理 API 速率限制。
-   不实现 Webhook 持续同步、后台队列和定时对账。

访问令牌不得作为普通数据写入
`localStorage`。授权会话与令牌存储方案在技术设计阶段确定。

## 12. 部署与技术边界

-   前端采用 Cordis 组织应用模块、服务和插件；浏览器运行方式、UI 框架及构建集成需通过技术调研验证（见 Issue #1）。
-   前端部署在 Vercel。
-   Vercel Functions 用于 GitHub App 授权流程、仓库挂载、GitHub
    写操作和配置同步。
-   配置解析、命名空间解析、状态过滤和频道选择等领域逻辑尽量使用纯
    TypeScript 模块，以便测试和复用。
-   第一版不部署常驻云
    Worker；如果实际测试证明托管函数不能满足需求，再单独评估。
-   不因预留多平台能力而提前实现其他 Git 适配器。

## 13. MVP 验收标准

-   [ ] 仓库 Owner / Maintainer 能安装/授权 GitHub App 并授予公开仓库访问范围；平台接入状态完全由当前 Installation 关系及其获准仓库集合决定，不需要第二次平台绑定。
-   [ ] 项目发现优先使用 GitHub Topic / Repository Search 获取候选项目卡片，不维护自建全局项目索引；如果授权过滤无法通过 GitHub App / GitHub API 的权威数据可靠验证，则将相关过滤或信息流后置。
-   [ ] 项目页从 Repo 根目录 `team-member.json` 读取团队成员，并在头像悬停时展示详细信息；平台编辑通过 Bot 身份提交文件，且服务端校验发起人的仓库写入权限。
-   [ ] Repo 动态读取所展示 Issue 的第一楼（Issue body），按 Markdown 和平台支持的扩展格式（包括视频外链）渲染；Issue 评论继续作为讨论内容。
-   [ ] 项目页面能读取并校验 `labourchain.config.yaml`。
-   [ ] 配置中缺少的 Label 定义能被创建。
-   [ ] 配置中声明的受管命名空间能正确清理 Issue 上的无效标签。
-   [ ] 未声明的命名空间不会被修改。
-   [ ] 空命名空间列表会清理对应 Issue
    标签；删除整个配置段落则停止管理。
-   [ ] 仓库级 Label 定义不会被本产品自动删除。
-   [ ] 看板只获取 Issue，不获取 PR。
-   [ ] 看板能使用配置中声明且具有有效标签的 Namespace 分列；当前 Namespace 内多个有效标签按配置顺序取最大值归列。
-   [ ] Closed Issue 默认隐藏，打开开关后可以分页查看。
-   [ ] 含 `status:archived` 的 Issue 在任何分列 Namespace 下默认隐藏，只有 Filter 明确包含 archived 后才显示。
-   [ ] 频道只选择最新创建的有效 Open Issue。
-   [ ] 删除 Wishlist 配置后，Wishlist 专用页面不再渲染。
-   [ ] 创建 Issue、回复评论和修改 Label 时遵守 GitHub 用户权限。
-   [ ] 按 `labour` YAML 格式解析 Issue 评论，支持必填 `work` 和
    以 0.5 小时为单位的主观估时 `hr`，以及可选 `commits`、
    `outcome`、`start-end`；无 Commit 的记录仍有效。
-   [ ] 结构化劳动记录能关联多个 Commit，且被包含的 Commit
    不重复生成基础记录。
-   [ ] 浏览器刷新和强制刷新行为清楚；缓存失败不会被伪装成最新数据。
-   [ ] GitHub API 或配置同步失败时，用户能看到失败状态，并可以重试。
