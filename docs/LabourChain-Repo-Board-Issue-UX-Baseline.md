## 1. 本阶段的范围与设计方向

- **已确认**：当前“项目”指**单个 GitHub Repository 在 LabourChain 上的项目工作区**。本阶段**不设计相似仓库或 Fork 聚合而成的跨仓库项目社区**；相关长期讨论单独放在 [#20](https://github.com/Ri0n72Y/hackathon-platform/issues/20)。
- **已确认**：LabourChain 的主界面不是 GitHub 的代码首页复刻，也不是传统 Jira/Linear 风格任务系统的重新着色。呈现上强调**工作、交流与劳动成果**；Issue 阅读默认**社区交流优先，任务管理按需展开**。
- **沿用约束**：第一版面向公开仓库，以 GitHub Issue/评论为真实数据源；不做 GitHub Projects、PR 看板、私有仓库、独立在线业务数据库或常驻 Webhook 同步。匿名用户可读，写操作按 GitHub 授权及具体权限执行。
- **沿用约束**：使用现有 Board/CardItem、DnD 等能力作为设计与实现基础；Cordis/插件拆分和 GitHub API/Vercel Functions 的职责另行按 #2 调研，不因 UI 决策提前认定底层已完成。

## 2. 页面与 URL 信息架构

| 页面 | 路由 | 主要职责 |
| --- | --- | --- |
| 平台入口 | `/` | 仓库选择/平台入口，不在本轮细化 |
| **仓库首页** | `/{owner}/{repo}` | Title + 精简项目介绍 → **限高看板预览** → Repo 动态 |
| **Kanban 专注页面** | `/{owner}/{repo}/kanban?filter=…&sort=…` | 更宽裕、更详细的看板浏览与管理；具体额外字段待设计 |
| **独立 Issue 详情** | `/{owner}/{repo}/issues/{number}` | 围绕话题的讨论、劳动记录、按需任务属性 |
| 频道 | 仓库路径下，具体模式待定 | 属于邻接模块，不在本轮扩展设计 |

- **已确认**：点击任意看板卡片，打开**独立 Issue 页面并更新 URL**；**不以右侧 Issue Drawer 作为默认导航**。
- **已确认**：两种看板使用相同 GitHub Issue 集合，均能选择仓库配置声明且有有效分列标签的 **Namespace**；`status:*` 是其中一种业务 Namespace，不是所有视图的唯一分列来源。进入专注页时继承适用的 Namespace、筛选/排序参数；普通视图条件以 URL 为可分享、可刷新、可用 Back/Forward 恢复的状态来源。
- **已确认**：独立 Issue 允许外部链接直达、刷新及浏览器前进/后退。浏览器返回原看板后应恢复 URL 所表示的过滤与排序；尽量恢复此前浏览位置（具体恢复策略待验证）。
- **沿用约束**：URL 只是资源位置，不代表 GitHub 登录、仓库授权或写权限。

## 3. 仓库首页（已确认）

**阅读层级：Title / 简短介绍 → 限高 Board → Repo 动态。**

1. 顶部展示仓库/项目名称和**类似 README 的简短背景**，提供阅读完整 README 和 GitHub 仓库的入口；不将整篇长 README 占满首屏。
2. 首页 Board 是**进度概览与快速进入工作的主区域**，但**限制可视高度**，避免项目动态永远被很多卡片埋在下方。
3. 通过清晰的“打开完整看板”入口进入独立 Kanban 工作页。首页预览仍应保留基本阅读、适用的筛选/排序和打开 Issue 的能力。
4. 看板下方是**Repo 动态**，选取**最近合并的 PR、近期 Commit Message、最近更新的 Issue 和新建 Issue**等 GitHub 来源；各来源按需读取、不依赖劳动记录跨 Issue 聚合。事件混排、去重、数量和刷新呈现留到页面实现时确定，不假定各源已经接入。
5. 不以推测的完成百分比或进度条替代真实的状态和记录。

**待验证**：Title 区具体高度、README 展开方式、限高值、列内/整体滚动、动态列表的可见性与性能、移动端布局。

## 4. Kanban 专注页与 Board 规则

### 4.1 布局、筛选、视图

- **已确认**：专注页给看板更充分的空间，允许更详细的任务信息和更完整的操作；它与首页预览**不是两套数据或独立保存的任务状态**。
- **已确认**：普通筛选与排序通过 URL 查询参数表示，当前选定的有效分列 Namespace 也属于可恢复视图条件；相同来源数据与相同参数应有**确定性的共有默认顺序**，而不是每个用户悄悄看到不同排序。精确 URL 参数 schema、控件分组、专注页密度仍待设计。
- **已确认**：团队共享的常用视图保存在仓库根 `labourchain.config.yaml` 的 `views` 列表，形如 `views: [{<name>: <filter string>}, ...]`；直接复用既有 Filter 字符串，个人视图可通过 URL/书签保存。现阶段不设计额外 views 配置文件或复杂视图系统。
- **已确认**：**同列卡片手动重排清空当前 Filter**，将界面标识为「**手动排序**」；只在当前页面会话中临时覆盖显示顺序，重新应用筛选/排序、刷新或重访 URL 后重置。**不写入 GitHub，也不保存跨用户/跨页面的私有持久化排列**；手动顺序不可分享，不能以不带 Filter 的 URL 声称恢复该排列。
- **已确认**：跨列拖动只在**当前选定 Namespace** 内操作：删除**当前所属列**的受管 Label，添加**目标列**的 Label；其他标签（包括同 Namespace 的其他有效标签）全部保留，**暂不区分独立/非独立标签**。校验权限/配置并反馈实际结果。若残留的标签在 config 中排位高于目标列，后续显示可能归入更大标签对应的列，不为此额外删除标签。

### 4.2 Label 与状态语义

- **已确认**：看板从仓库配置声明的有效 Namespace 中选择分列；**标签顺序按 config 从小到大**，当 Issue 在所选 Namespace 下有多个有效标签，默认按**最大标签**决定唯一显示列；没有有效标签则不归入普通列，不再要求恰好一个标签。`status:*` 是整体业务状态 Namespace，但不是所有看板唯一分列来源。
- **已确认**：Issue 含 `status:archived` 时，**无论当前选择哪个 Namespace** 都默认隐藏；仅当用户在 Filter 勾选「包含 archived」才纳入。GitHub Open/Closed 与标签状态是另一维度，Closed 默认隐藏；归档包含条件不自动意味着包含 Closed。
- **已确认**：`version:*` 默认关闭、按需启用，业务标签允许多选；一个 Issue 仍只有一个整体 status，并不产生各版本独立 Doing/Done。选择 `version` 等 Namespace 分列时，**以配置排序最大的有效标签归列**，不因多选排除该 Issue。
- **沿用约束**：`channel:*` 仍作为频道识别依据，但频道使用体验属于另行研究；同一有效 Issue 可以同时被看板与频道关联。

### 4.3 CardItem 信息层级

- **已确认·当前范围**：看板卡片以任务标题、Issue 编号、当前多个 Assignees 等任务信息为主；**不展示 Labour Record、`outcome`、劳动记录作者或累计工时**。这些仅在对应 Issue 详情内按需读取，不为每张卡片批量加载评论。
- **已确认**：紧凑模式只降低任务信息密度，不重新加入劳动摘要或统计，不虚构参与者、完成进度或成果。
- **尚待确定**：是否显示 Branch（仅当有可靠来源）、专注页增加哪些任务字段及卡片尺寸。卡片不再设计劳动 `outcome` / `work` 回退展示。

## 5. Issue 详情：社区交流优先（已确认）

- **已确认**：独立页面路由 `/{owner}/{repo}/issues/{number}`；**不是**点击看板后在原页面右侧展开的详情抽屉。
- **已确认**：Issue 页面以**社区交流和劳动进展**为主视觉，借鉴 Discord 的话题参与感，避免复制 GitHub Issue 的完整任务管理界面。
- **已确认**：左右侧栏**默认均隐藏**，且可独立展开。左侧用于项目工作区导航；右侧用于任务属性（status、Assignees、版本、标签等），让用户按需进入更像任务管理的体验。侧栏展开不改变 Issue URL。
- **已确认**：Issue 主内容包括话题标题/身份、**仅该 Issue 的近期劳动成果及主观登记工时摘要**、原始正文/背景，以及下方固定的「讨论 / 劳动历史」两个 Tab；不将劳动记录重复显示在普通讨论中。这里只做**单 Issue 内的局部汇总**，不做仓库或平台统计。
- **已确认**：讨论消息强调作者、时间、自然的对话流，**不伪装成实时 IM**；内容来自 GitHub Issue 普通评论，保留原始来源及必要的加载/刷新反馈。是否默认折叠较长话题正文仍需检验。
- **已确认**：**讨论输入采用靠近讨论底部的 Discord 式可达位置 + 明确的 GitHub 提交反馈**：默认简洁、展开多行 Markdown，提交有写入中/成功/失败状态。究竟固定在视口还是内容底部、草稿如何自动恢复仍待原型验证。
- **已确认**：**劳动历史 Tab 使用结构化登记表单**；提交的数据写回 GitHub Issue 评论，并按现有的**独立 Labour Record 规则**解析。手动通过 GitHub 添加符合现行规则的结构化评论与 UI 表单生成记录应能被同等读取，不强制劳动者必须通过 UI 填写；本阶段不改写劳动记录协议或接入完整 LabourChain 协议。
- **已确认**：劳动历史贡献者和当前 Assignees 不是同一集合，不能因为某人登记劳动就自动赋予当前 Assignee 身份。有效 Labour Record 的历史贡献者依记录作者归属，记录需允许关联原 GitHub 评论。

### 阅读位置（本地 KV）

- **已确认**：首次打开 Issue，从话题上下文顶部开始；再次访问优先接续之前阅读的讨论，若出现新回复则优先定位到第一条未读回复，并可看见未读分界线。
- **已确认**：阅读进度**仅保存在当前浏览器本地 KV**，不写 GitHub、也不跨浏览器/设备同步；键应至少区分仓库、Issue，以及适用时的当前用户身份。
- **已确认**：不要在页面加载时直接将全部内容自动设为已读；应以用户实际可见的阅读位置更新。无本地数据时退回首次访问体验，用户可随时回到话题顶部。
- **待验证**：最后已读评论 ID、最近浏览时间、滚动锚点等具体 KV schema，以及讨论/劳动 Tab 的阅读位置是否分别记忆。

## 6. Assignees、Contributors、劳动与异常

- **已确认**：**Assignees** 表示目前正在参与该 Issue 的人，可以是**多人**；使用 GitHub 已有的 Assignee 权限模型。具备 GitHub 权限的用户可以管理符合资格的 Assignees；不设计额外的独立“认领”安全模型。
- **已确认**：在**当前 Issue 详情**中，Contributors 指该 Issue 上通过可识别劳动记录登记工作的历史参与者；即使已不担任 Assignee，其该 Issue 内的劳动历史仍保留。此处不是仓库级 Contributors 统计，也不要求跨 Issue 的参与者汇总。
- **已确认**：Doing 中无 Assignee 是**可审计异常**，提供提示/筛选但**不自动补人或修复**；Todo 未分配是正常情况。
- **已确认**：如展示累计工时，仅统计**当前 Issue 内已有 Labour Record 的主观登记时长**；没有记录不代表没有劳动，不虚构真实工时、完成度或 `outcome`。**跨 Issue、仓库或平台的整体劳动统计等自有后端建立后再设计**。
- **沿用约束·用户再次确认**：劳动记录使用现行独立 Labour Record 规则，来源仍为 GitHub Issue 结构化评论及相关 Commit；Issue 页面只处理**当前 Issue 关联的记录与 Commit**，不为整体统计遍历其他 Issue 评论或仓库 Commit。旧 MVP YAML 示例不是严格新 Schema；不接入完整 LabourChain 协议，也不做链上价值计算。

## 7. 关键交互与反馈边界

| 情境 | 行为契约 |
| --- | --- |
| 点击首页或 Kanban 卡片 | 正常导航到独立 Issue URL；返回恢复 URL 驱动的过滤/排序 |
| 跨列拖动 | 授权后只移除当前列标签、添加目标列标签；保留其余标签，按最大剩余标签规则重新归列；有提交中/确认/失败反馈，失败恢复并可重试 |
| 同列拖动 | 清空当前 Filter，标识「手动排序」；仅在当前页面临时调整顺序，不写入 GitHub，也不产生可分享或跨页面持久排列 |
| 发表普通评论 | 通过 GitHub 授权路径写入；写入前后明确反馈，不提前显示为已持久成功 |
| 登记劳动 | 在当前 Issue 的劳动 Tab 使用结构化表单，写入符合现行独立规则的 GitHub 评论；失败保留输入，不触发整体劳动统计 |
| 无权限 / GitHub 未登录 | 公开内容可读；写操作按真实权限提示登录/授权/缺少权限，不能假装写入 |
| 空配置 / 无匹配 Issue / 加载失败 | 给出可理解的空态、重试/恢复路径，区分“没有记录”与“读取失败” |
| GitHub 写入后的数据可见性 / 缓存过期 | 写入成功以接口实际结果确认；后续读取可能延迟约 1–2 分钟才反映变更（用户实测、非保证时限），允许手动刷新，不假称实时同步；失败仍明确反馈 |

以上属于应落实的交互契约；具体组件、网络时序及验证用例还需要结合实现/原型审查。

## 8. AI-native 后续特色能力（不是本轮 MVP 承诺）

- **已确认的未来方向**：页面可展示项目/当前话题的**基本背景与近期动态摘要**，右侧侧栏可以呈现**Agent 对话窗口**；基于用户 Profile 的个性化建议属于更远期方向。Agent 与任务属性侧栏如何共存**未定**。
- **已确认的初步实验边界**：最小 Context Harness 自动带入项目背景和当前浏览页面；用户**自行配置 API Key（BYOK）**，明确标识“实验/测试”；只保存在当前浏览器本地，更换浏览器/设备或清空本地数据需重新配置。
- **待调研**：Vercel Function 是否适合作为简单的 Chat Stream 转发层、流式协议/供应商兼容、密钥处理及成本、权限、上下文范围、来源可信度、日志防护与用户告知。**本地保存 Key 不等于本地推理**：代理方案仍会向服务端及模型供应商传输必要内容。
- **边界**：初期 Agent 仅辅助阅读、总结和问答，**不默认赋予 GitHub 写入能力**；不能将未验证方案写作当前已具备的能力。

## 9. 尚未确定、下一轮才需要评估的事项

1. **Kanban 专注页**：工具栏层次、完整卡片额外字段、默认/紧凑密度、桌面与触屏拖拽反馈和大数据量下的滚动。
2. **首页 Board**：限高数值、列内滚动 vs 其他受控预览、移动端列切换；README 摘要长度和仓库动态事件范围。
3. **导航细节**：从首页/专注页进入 Issue 后保留返回来源、URL 查询参数精确命名、浏览位置锚点恢复。
4. **Issue 主体**：长正文默认展开/折叠、讨论输入框是否 sticky、左右面板窄屏行为与草稿保持。
5. **现有 Issue 内劳动记录的接入验证**：按现行独立规则核对字段/解析，确认本 Issue 的手工评论与 UI 表单写入一致；不实施跨 Issue 总统计或完整 LabourChain 协议。
6. **配置**：已确定根配置 `views` 存放常用 Filter；后续核对实际配置字段/读取与变更权限，以及当前 Namespace 的无效标签、写入失败处理，不另设计重复的视图存储机制。
7. **验证**：真实可交互原型的加载、空态、权限、失败重试、键盘可达性、直接链接与浏览器历史的认知走查。

**后续工作优先级**：继续 #2，先细化**Kanban 专注页面的工具栏、卡片密度、操作反馈**，然后用代表性场景走查首页 → Kanban → Issue → 返回的完整链路。不要将 #20 的跨仓库社区愿景或未来 AI 能力混入本次 MVP 交付范围。
