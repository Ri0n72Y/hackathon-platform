## 1. 本阶段的范围与设计方向

- **已确认**：当前“项目”指**单个 GitHub Repository 在 LabourChain 上的项目工作区**。本阶段**不设计相似仓库或 Fork 聚合而成的跨仓库项目社区**；相关长期讨论单独放在 [#20](https://github.com/Ri0n72Y/hackathon-platform/issues/20)。
- **已确认**：LabourChain 的主界面不是 GitHub 的代码首页复刻，也不是传统 Jira/Linear 风格任务系统的重新着色。呈现上强调**工作、交流与劳动成果**；Issue 阅读默认**社区交流优先，任务管理按需展开**。
- **沿用约束**：第一版面向公开仓库，以 GitHub Issue/评论为真实数据源；不做 GitHub Projects、PR 看板、私有仓库、独立在线业务数据库或常驻 Webhook 同步。匿名用户可读，写操作按 GitHub 授权及具体权限执行。
- **沿用约束**：使用现有 Board/CardItem、DnD 等能力作为设计与实现基础；Cordis/插件拆分和 GitHub API/Vercel Functions 的职责另行按 #2 调研，不因 UI 决策提前认定底层已完成。
- **新增范围原则（2026-10-29）**：优先使用 GitHub 原生能力和现有仓库数据；MVP 不建立或人工维护独立的全局项目索引、项目注册表或跨仓库聚合数据。项目发现优先使用 GitHub Topic / Repository Search；如果授权过滤等功能必须依赖自建全局数据，则移出 MVP 或后置。

## 2. 页面与 URL 信息架构

| 页面 | 路由 | 主要职责 |
| --- | --- | --- |
| 平台入口 | `/` | 仓库选择/平台入口，不在本轮细化 |
| **仓库首页** | `/{owner}/{repo}` | Title + 精简项目介绍 → 单行成员头像与 Hover 详情卡片 → Repo 动态；第一版不展示看板 |
| **成员展示页** | `/{owner}/{repo}/members` | 展示 `team-member.json` 中的全部成员资料，并提供添加入口 |
| **成员登记页** | `/{owner}/{repo}/members/register` | 项目管理者通过简单表单添加成员；由 GitHub App Bot 提交 Commit 或 PR |
| **Kanban 专注页面（后置）** | `/{owner}/{repo}/kanban?filter=…&sort=…` | 独立看板页面；保留既有设计，后置实现，不嵌入项目主页 |
| **独立 Issue 详情** | `/{owner}/{repo}/issues/{number}` | 围绕话题的讨论、劳动记录、按需任务属性 |
| 频道 | 仓库路径下，具体模式待定 | 属于邻接模块，不在本轮扩展设计 |

- **已确认**：点击任意看板卡片，打开**独立 Issue 页面并更新 URL**；**不以右侧 Issue Drawer 作为默认导航**。
- **已确认（后续 Kanban 阶段）**：看板依配置选择有效分列 Namespace，`status:*` 不是唯一选择；`status:archived` 在任何 Namespace 下默认隐藏。选定 Namespace 与普通 Filter/排序通过 URL 可分享、可刷新、可用 Back/Forward 恢复。第一版首页不含 Board 预览，不能再用“首页和专注页两种看板”描述当前版本。
- **已确认**：独立 Issue 允许外部链接直达、刷新及浏览器前进/后退。浏览器返回原看板后应恢复 URL 所表示的过滤与排序；尽量恢复此前浏览位置（具体恢复策略待验证）。
- **沿用约束**：URL 只是资源位置，不代表 GitHub 登录、仓库授权或写权限。

## 3. 仓库首页（已确认）

**第一版项目主页层级：Title / 简短介绍 → 团队成员头像与悬浮详情 → Repo 动态。项目主页不展示 Board。** 看板保留为独立 Kanban 页面，后置实现。
**设计与排期区分（2026-11-05）：** Kanban 的可选 Namespace、标签归列、筛选、团队视图和拖动规则仍是有价值的**后续开发设计**，不是被废弃的方案。旧 #23 的首页限高 Board 预览与先开发 Kanban 的顺序仅不属于**当前 MVP 首版交付**；可作为未来阶段设计依据，若要重新纳入首页需另行调整本版范围。参见 [PR #23](https://github.com/Ri0n72Y/hackathon-platform/pull/23)。

1. 顶部展示仓库/项目名称和**类似 README 的简短背景**，提供阅读完整 README 和 GitHub 仓库的入口；不将整篇长 README 占满首屏。
2. **团队成员**：项目主页仅展示一行头像；桌面鼠标悬停头像时显示该成员详情卡片，键盘聚焦可打开同一卡片，触屏点击打开锚定卡片。数据从所选展示分支根目录 `team-member.json` 读取。完整资料页与登记页分别为 `/{owner}/{repo}/members` 和 `/{owner}/{repo}/members/register`。GitHub 账号选填；成员可以使用自定义头像 URL 或姓名首字母占位。参与者仍可手动维护 JSON；平台登记由 GitHub App Bot 提交，服务端先校验当前登录操作者的仓库写入权限。
3. **Repo 动态**：读取所展示 GitHub Issue 的第一楼（Issue body），将其作为 Markdown 文档渲染，并支持平台扩展格式，包括视频外链；Issue 评论仍用于讨论，不替代第一楼正文。每条动态应保留原 Issue 的来源链接。
4. 不以推测的完成百分比或进度条替代真实的状态和记录。
5. 第一版项目主页不显示 Board 预览，也不提供嵌入首页的看板交互。看板保留为独立 Kanban 页面，后置实现。

**待验证**：Title 区具体高度、README 展开方式、限高值、列内/整体滚动、动态列表的可见性与性能、移动端布局。

### 3.1 团队成员展示与登记（D1–D3 已收敛，D4 待验证）

#### A. 项目主页 Team 区：一行头像

- **只保留一行头像**，不显示头像网格，不在头像下方常驻姓名或角色，不把头像点击改成抽屉/侧栏。桌面头像建议 40×40px，窄屏 36×36px，圆形，间距 8px；头像按钮有清晰的键盘焦点环。
- 头像行不换行。成员过多时横向滚动；右侧提供「查看全部成员」链接，进入 `/members`。不使用虚构的成员上限或统计数字。
- 头像图片优先级：有效 `avatarUrl` → 有 GitHub 账号时使用其 GitHub 头像 → 姓名首字母占位。图片加载失败也回退到首字母。
- `team-member.json` 缺失、有效但为空、格式无效和读取失败是不同状态。只影响 Team 区，不阻断项目介绍与 Repo 动态。

#### B. Hover 详情卡片

- 桌面使用**可交互 Popover 卡片**，不使用只能展示短文本的 Tooltip。建议宽度 300px、最大高度 360px；窄屏宽度不超过视口宽度减 24px。卡片锚定头像，优先显示在头像下方；空间不足时自动翻转/偏移，避免超出视口。
- 卡片内容顺序：成员头像、显示名称、角色（有值才显示）、个人介绍（最多显示 4 行，超出省略）、GitHub 主页（有账号才显示）、其他资料链接（最多 3 条）。缺失字段直接省略，不填造默认身份或简介。
- 鼠标进入头像后短暂延迟打开（建议约 120ms）；鼠标从头像移入卡片时保持打开；离开头像和卡片整体区域后关闭（建议约 180ms 延迟，避免指针移动造成闪烁）。卡片内链接可正常点击。
- 键盘 Tab 聚焦头像时打开同一卡片；Enter/Space 可切换；Escape 关闭并将焦点留在触发头像上。Popover 非模态，不锁定焦点。触屏点击头像打开同一锚定卡片，再次点击、点击外部或 Escape 关闭；点击另一个头像时切换到对应成员。**不另做移动端抽屉**。
- 头像按钮的可访问名称使用成员显示名称；Popover 与触发器建立 `aria-controls` / `aria-expanded` 关系，卡片出现和关闭不偷走焦点。

#### C. 成员展示页 `/{owner}/{repo}/members`

- 页面标题为「团队成员」，可显示由 JSON 实际读取的成员数量。资料按 `members` 数组顺序展示，新登记成员追加在末尾；不按 GitHub 活跃度、角色或姓名暗中重排。
- 桌面使用两列资料卡片，窄屏单列；页面内容最大宽度约 960px。每张卡片展示 56px 头像、姓名、角色、完整纯文本简介、GitHub 主页和其他链接。主页头像行与成员页使用同一头像回退规则。
- 右上角提供「添加成员」入口。匿名用户看到「登录后添加成员」并在 OAuth 后返回原 URL；已登录但无 Repo 写权限时说明当前账号无写权限，不开放提交表单；只有服务端确认权限后才进入可提交状态。
- MVP 只提供成员浏览与新增，不加入搜索、筛选、编辑、删除、邀请或平台账号绑定。需要修改/移除成员时，维护者可按既有约定手动维护 `team-member.json`；后续若增加编辑能力另行设计。
- 有效空数组显示「暂无成员」；文件不存在显示「尚未添加团队成员」并为有权限者提供添加入口；JSON 无效显示文件格式错误及 GitHub 文件入口，不允许表单静默覆盖；网络失败显示重试，不误报为空。

#### D. 新成员登记页 `/{owner}/{repo}/members/register`

- 使用单列表单，内容宽度约 640px；面包屑为「项目 / 团队成员 / 添加成员」，标题「添加团队成员」。表单顶部显示当前已验证的 GitHub 操作者账号，以及只读目标分支标记「提交到 `<displayBranch>`」。
- **目标分支固定为当前展示分支**，不在简单登记表单中增加分支选择器，避免成员提交到另一个分支后仍未出现在当前主页。若项目切换展示分支，登记目标随之变化；分支不存在或不可写时明确报错。
- 字段与校验：
  - `name` 显示名称：必填，去除首尾空格后 1–60 字符。
  - `role` 项目角色：选填，最多 40 字符。
  - `githubUsername` GitHub 用户名：选填，1–39 字符；填写时校验 GitHub 用户名格式并由服务端确认账号存在。留空完全合法。
  - `bio` 个人介绍：选填，最多 280 字符，按纯文本显示，不支持任意 Markdown/HTML。
  - `avatarUrl` 头像图片 URL：选填，仅接受 HTTPS；未填写时优先使用 GitHub 头像，没有 GitHub 账号则使用姓名首字母。MVP 不做图片上传。
  - `links` 个人链接：选填，最多 3 条；每条包含显示名称（1–24 字符）和 HTTPS URL。空项不保存。
- 表单只展示必要字段，不要求邮箱、手机号、平台账号或成员本人登录；GitHub 账号是可选的公开资料关联，不作为成员身份或参与资格。
- 提交按钮为「提交成员资料」，取消返回 `/members`。提交前清晰说明「由 LabourChain Bot 提交，GitHub 操作者为 @login」；不再增加重复的二次确认弹窗。
- 服务端生成稳定且唯一的 `id`；新增记录追加到数组末尾。若 `githubUsername` 已存在（忽略大小写），阻止重复添加并提供现有成员入口；相同显示名称允许存在。

#### E. `team-member.json` 最小数据契约

```json
{
  "version": 1,
  "members": [
    {
      "id": "stable-id",
      "name": "Display name",
      "role": "Project role",
      "bio": "Plain-text introduction",
      "githubUsername": "github-login",
      "avatarUrl": "https://example.com/avatar.png",
      "links": [{ "label": "Website", "url": "https://example.com" }]
    }
  ]
}
```

- `version` 与 `members` 为顶层字段；`id`、`name` 必填，其余字段选填。空的选填字段省略，不写入空字符串。`id` 由登记服务生成；手动维护时必须保持唯一且稳定。字段顺序不影响读取，`members` 数组顺序决定页面展示顺序。
- JSON 结构无效时只读报错，不自动覆盖。文件不存在时允许在目标分支初始化。简介作为纯文本安全渲染；所有头像/外链仅允许 HTTPS，禁止 `javascript:`、`data:` 等协议。

#### F. Bot Commit / PR 与操作者归属

- User OAuth 会话用于取得真实操作者身份并验证其对目标 Repo 的实际写入权限；GitHub App Installation Token 用于以 Bot 身份写入文件。两者职责分离，不将 Bot 写入伪装成用户本人提交。
- 服务端从已验证会话取得操作者 GitHub login，不信任浏览器传入的用户名；每次写入重新验证 Repo Installation、操作者权限、目标分支和固定文件路径 `team-member.json`，并校验 CSRF/同源请求。
- 读取目标分支当前文件及 Blob SHA 后追加成员。文件不存在时初始化；格式无效时停止；SHA 冲突时重读最新文件并重新计算追加，不能覆盖并发成员。
- 目标分支允许 Bot 直接写入时创建 Commit；若 GitHub 分支保护/Ruleset 阻止直接写入，则 Bot 创建唯一维护分支并向目标分支发起 PR。**不绕过保护、不自动合并**。Commit Author 保持 Bot；Commit message 与 PR 正文明确记录 `Requested by @login` 及其 GitHub 主页链接。
- Commit 成功后重读当前展示分支并刷新成员列表。PR 创建成功但未合并时显示「等待仓库维护者审核/合并」和 PR 链接，成员列表仍读取原展示分支，不提前显示 PR 分支内容；合并后由用户刷新/重新进入页面读取新版本，不承诺后台轮询。
- 失败时保留表单：401 引导登录并返回原路由；403 说明缺少仓库写权限；409/SHA 冲突重新读取并提示安全重试；无效 JSON 阻止写入；429 尊重 GitHub 限流反馈；网络/5xx 提供手动重试，不自动无限重试。
- **实施前技术门槛**：#5 的现有记录只确认 GitHub App Issues Read/Write 与 Metadata Read；Bot 写入尚未完成真实验证。Coder 必须先核对当前 App 是否具备 Contents Write；若需 PR，还须核对 Pull Requests Write。缺少权限时不能假设可用，也不能擅自扩权；须单独说明权限缺口与批准流程。

**范围边界**：本节确定交互与最小数据契约，不表示代码、GitHub App Bot 写入或线上权限已实现/验证；真实权限、分支保护和 GitHub API 结果始终优先于界面预期。

## 4. Kanban 专注页与 Board 规则（后续阶段）

本节保留已确认的独立看板设计约束，供后续实现使用。第一版项目主页不展示看板，独立 Kanban 页面也后置实现。

### 4.1 布局、筛选、视图

- **已确认（后续阶段）**：独立 Kanban 页面给看板更充分的空间，允许更详细的任务信息和更完整的操作。看板页面实现后复用 GitHub Issue 数据；第一版首页不提供预览，因此不存在首页预览与独立看板之间的双视图交互。
- **已确认（后续 Kanban 阶段）**：选定分列 Namespace、普通 Filter 和排序通过 URL 查询参数表达；相同数据与参数应有确定性的共有默认顺序。同列手动顺序不是可分享 URL 状态。精确参数 schema、控件分组、专注页密度仍待设计。
- **已确认（后续 Kanban 阶段）**：可由仓库配置声明团队共享视图，个人使用 URL/书签保留视图，不自动写回仓库。#23 的已有设计记录采用根 `labourchain.config.yaml` 的 `views` 列表保存名称与 Filter 字符串，不引入另一个持久视图系统；具体字段/解析契约在实现时核对。
- **已确认（后续 Kanban 阶段）**：同列手动重排**清空当前 Filter、显示「手动排序」**，只在当前页面会话临时覆盖顺序，重新筛选/排序、刷新、重访 URL 后重置；不写入 GitHub、不存跨用户持久顺序、不宣称链接能恢复手动排列。#23 还保留 `pinned` 优先设计记录，实施前核对相应数据契约，不因此新增字段。
- **已确认（后续 Kanban 阶段）**：跨列拖动只移除**当前选定 Namespace 的来源列标签**、添加目标列标签，保留同 Namespace 其余有效标签、其他 Namespace 标签及普通属性，不另造独立/非独立标签类别。重新读取按最大有效标签归列，可能出现回到更大标签列的结果；需实际授权、明确反馈与失败恢复。

### 4.2 Label 与状态语义

- **已确认**：看板可选择 `labourchain.config.yaml` 中已声明且有效标签列表非空的任一 Namespace 分列，`status:*` 不是唯一分列来源。标签顺序按配置从小到大；同一 Issue 在当前 Namespace 有多个有效标签时，归入配置顺序中最大的有效标签所在列；没有有效标签则不进入该 Namespace 的普通列。
- **已确认**：只要 Issue 含 `status:archived`，无论当前分列 Namespace 是什么，默认都隐藏；只有 Filter 明确选择「包含 archived」后才纳入候选结果。GitHub 的 Open/Closed 是**与业务 status 不同的维度**。Closed 默认隐藏，用户打开开关后再分页读取。
- **已确认**：`version:*` 是**用户主动启用、默认关闭**的可选标签命名空间，支持**多选**。同一 Issue 可涉及多个版本，在正文中分别解释各版本工作；`status:*` 仍表达整体状态，但若存在多个有效状态标签，按配置顺序取最大值作为当前有效状态。不得由版本标签推出每个版本各自的 Done/Doing，也不自动将旧版本判定完成。
- **沿用约束**：`channel:*` 仍作为频道识别依据，但频道使用体验属于另行研究；同一有效 Issue 可以同时被看板与频道关联。

### 4.3 CardItem 信息层级

- **已确认的平衡默认密度方向**：任务标题与 Issue 编号、多个当前 Assignees 的头像/身份、**最新有效 Labour Record 的 outcome 与记录作者**，以及**累计已登记的主观工时**（不能视为客观实际投入）。
- **已确认**：紧凑模式可隐藏较长的成果行和最近贡献者信息，不应虚构缺失的成果、参与者或完成进度。
- **尚待确定**：无 outcome 时是否回退展示 `work` 的片段、是否显示 Branch（仅在有可靠来源时）、专注页增加哪些字段以及默认卡片尺寸。
- **设计版本差异（待后续 Kanban 阶段确认）：** 2026-10-28 的 #23 方案要求 CardItem **不显示** Labour Record/`outcome`/工时；上方记录另一版**显示**最新劳动成果/主观工时。两者均保留为设计历史，需产品方与 Designer 最终确认卡片密度；不能因 Kanban 开发后置就认定 #23 设计无效。

## 5. Issue 详情：社区交流优先（已确认）

- **已确认**：独立页面路由 `/{owner}/{repo}/issues/{number}`；**不是**点击看板后在原页面右侧展开的详情抽屉。
- **已确认**：Issue 页面以**社区交流和劳动进展**为主视觉，借鉴 Discord 的话题参与感，避免复制 GitHub Issue 的完整任务管理界面。
- **已确认**：左右侧栏**默认均隐藏**，且可独立展开。左侧用于项目工作区导航；右侧用于任务属性（status、Assignees、版本、标签等），让用户按需进入更像任务管理的体验。侧栏展开不改变 Issue URL。
- **已确认**：Issue 主内容包括话题标题/身份、**只取当前 Issue 有效记录**的最近劳动成果、作者与主观登记工时摘要、GitHub Issue 原始正文/话题背景及下方的 **Tab：讨论 / 劳动历史**。有效劳动评论不在普通讨论重复显示；分页未完、数据冲突/来源不足时不宣称统计完整。
- **已确认**：讨论消息强调作者、时间、自然的对话流，**不伪装成实时 IM**；内容来自 GitHub Issue 普通评论，保留原始来源及必要的加载/刷新反馈。是否默认折叠较长话题正文仍需检验。
- **已确认**：**讨论输入采用靠近讨论底部的 Discord 式可达位置 + 明确的 GitHub 提交反馈**：默认简洁、展开多行 Markdown，提交有写入中/成功/失败状态。究竟固定在视口还是内容底部、草稿如何自动恢复仍待原型验证。
- **已确认**：**劳动历史 Tab 使用独立结构化登记表单**；提交的数据写回 GitHub 允许的评论路径，并由 Labour Record 解析器识别。手动通过 GitHub 添加符合**最新劳动记录协议**的 YAML 评论与 UI 表单生成记录应能被同等读取，不强制劳动者必须通过 UI 填写。
- **已确认**：劳动历史贡献者和当前 Assignees 不是同一集合，不能因为某人登记劳动就自动赋予当前 Assignee 身份。有效 Labour Record 的历史贡献者依记录作者归属，记录需允许关联原 GitHub 评论。

### 阅读位置（本地 KV）

- **已确认**：首次打开 Issue，从话题上下文顶部开始；再次访问优先接续之前阅读的讨论，若出现新回复则优先定位到第一条未读回复，并可看见未读分界线。
- **已确认**：阅读进度**仅保存在当前浏览器本地 KV**，不写 GitHub、也不跨浏览器/设备同步；键应至少区分仓库、Issue，以及适用时的当前用户身份。
- **已确认**：不要在页面加载时直接将全部内容自动设为已读；应以用户实际可见的阅读位置更新。无本地数据时退回首次访问体验，用户可随时回到话题顶部。
- **待验证**：最后已读评论 ID、最近浏览时间、滚动锚点等具体 KV schema，以及讨论/劳动 Tab 的阅读位置是否分别记忆。

## 6. Assignees、Contributors、劳动与异常

- **已确认**：**Assignees** 表示目前正在参与该 Issue 的人，可以是**多人**；使用 GitHub 已有的 Assignee 权限模型。具备 GitHub 权限的用户可以管理符合资格的 Assignees；不设计额外的独立“认领”安全模型。
- **已确认**：**当前 Issue 的 Contributors** 是该 Issue 中有可识别劳动记录的历史作者，即使不再是 Assignee 仍保留该 Issue 贡献历史；不混同 GitHub 仓库 Contributors，也不进行跨 Issue 汇总。
- **已确认**：Doing 中无 Assignee 是**可审计异常**，提供提示/筛选但**不自动补人或修复**；Todo 未分配是正常情况。
- **已确认**：Issue 详情只统计**当前 Issue 有效、已获取的结构化劳动记录**中的主观估计小时数；缺失不能推算真实工时、完成度或虚构 `outcome`。评论分页未全、引用 Commit 冲突或来源不明时标注不完整，不扫描全仓库/其他 Issue 汇总。
- **已确认（2026-11-05）**：本项目 Labour Record 协议是 [`LabourChain-MVP-Product-Spec.md` §9.4](./LabourChain-MVP-Product-Spec.md#94-labour-record)，以 GitHub YAML 结构化评论及可靠关联 Commit 为来源。`hr: ~1.5` 和 `hr: ~1.5h` 均合法，统一解析为数字 `1.5` 小时，其他 0.5 小时增量同理；不计算劳动价值。

## 7. 关键交互与反馈边界

| 情境 | 行为契约 |
| --- | --- |
| 点击独立 Kanban 页面中的卡片（看板实现后） | 导航到独立 Issue URL；返回恢复 URL 驱动的过滤/排序 |
| 跨列拖动 | 授权后仅写入当前选定 Namespace 的来源/目标标签；保留其他标签；有提交中/确认/失败反馈，失败恢复原状并可重试 |
| 同列拖动 | 仅临时调整当前视图顺序，不写入 GitHub，也不产生跨页面持久排列 |
| 发表普通评论 | 通过 GitHub 授权路径写入；写入前后明确反馈，不提前显示为已持久成功 |
| 登记劳动 | 在当前 Issue 的劳动 Tab 用结构化表单写入符合 §9.4 的 GitHub 评论，写权限取决于用户 OAuth 实际授权，失败保留输入；写入确认与随后是否读到该评论分别显示 |
| Hover 成员头像 | 打开锚定的非模态详情卡片；指针可移入卡片，键盘聚焦与触屏点击均可达；Escape/外部点击关闭 | 卡片定位、焦点顺序、窄屏溢出与屏幕阅读器走查 |
| 浏览成员页 | `/members` 按 JSON 数组顺序展示完整资料；无 GitHub 账号仍可展示 | 缺失/空文件/无效 JSON/网络失败状态走查 |
| 登记成员 | `/members/register` 校验权限后显示表单；Bot Commit 或 PR，记录真实操作者；PR 未合并不提前显示成员 | GitHub App Contents/PR 权限、分支保护、SHA 冲突与真实写入验收 |
| 无权限 / GitHub 未登录 | 公开内容可读；写操作按真实权限提示登录/授权/缺少权限，不能假装写入 |
| 空配置 / 无匹配 Issue / 加载失败 | 给出可理解的空态、重试/恢复路径，区分“没有记录”与“读取失败” |
| GitHub 写入后的读取 / 缓存过期 / 分页 | 仅 GitHub 确认后才提示写入成功；随后读取可能尚未可见，应允许刷新并如实显示当前读取/分页状态，不保证固定同步时限，也不以部分页面或缓存称作实时完整数据 |

以上属于应落实的交互契约；具体组件、网络时序及验证用例还需要结合实现/原型审查。

## 8. AI-native 后续特色能力（不是本轮 MVP 承诺）

- **已确认的未来方向**：页面可展示项目/当前话题的**基本背景与近期动态摘要**，右侧侧栏可以呈现**Agent 对话窗口**；基于用户 Profile 的个性化建议属于更远期方向。Agent 与任务属性侧栏如何共存**未定**。
- **已确认的初步实验边界**：最小 Context Harness 自动带入项目背景和当前浏览页面；用户**自行配置 API Key（BYOK）**，明确标识“实验/测试”；只保存在当前浏览器本地，更换浏览器/设备或清空本地数据需重新配置。
- **待调研**：Vercel Function 是否适合作为简单的 Chat Stream 转发层、流式协议/供应商兼容、密钥处理及成本、权限、上下文范围、来源可信度、日志防护与用户告知。**本地保存 Key 不等于本地推理**：代理方案仍会向服务端及模型供应商传输必要内容。
- **边界**：初期 Agent 仅辅助阅读、总结和问答，**不默认赋予 GitHub 写入能力**；不能将未验证方案写作当前已具备的能力。
