## 1. 本阶段的范围与设计方向

- **已确认**：当前“项目”指**单个 GitHub Repository 在 LabourChain 上的项目工作区**。本阶段**不设计相似仓库或 Fork 聚合而成的跨仓库项目社区**；相关长期讨论单独放在 [#20](https://github.com/Ri0n72Y/hackathon-platform/issues/20)。
- **已确认**：LabourChain 的主界面不是 GitHub 的代码首页复刻，也不是传统 Jira/Linear 风格任务系统的重新着色。呈现上强调**工作、交流与劳动成果**；Issue 阅读默认**社区交流优先，任务管理按需展开**。
- **沿用约束**：第一版面向公开仓库，以 GitHub Issue/评论为真实数据源；不做 GitHub Projects、PR 看板、私有仓库、独立在线业务数据库或常驻 Webhook 同步。匿名用户可读，写操作按 GitHub 授权及具体权限执行。
- **沿用约束**：使用现有 Board/CardItem、DnD 等能力作为设计与实现基础；Cordis/插件拆分和 GitHub API/Vercel Functions 的职责另行按 #2 调研，不因 UI 决策提前认定底层已完成。

## 2. 页面与 URL 信息架构

| 页面 | 路由 | 主要职责 |
| --- | --- | --- |
| 平台入口 | `/` | 仓库选择/平台入口，不在本轮细化 |
| **仓库首页** | `/{owner}/{repo}` | Title + 精简项目介绍 → 成员头像悬浮详情 → Repo 动态；第一版不展示看板 |
| **Kanban 专注页面（后置）** | `/{owner}/{repo}/kanban?filter=…&sort=…` | 独立看板页面；保留既有设计，后置实现，不嵌入项目主页 |
| **独立 Issue 详情** | `/{owner}/{repo}/issues/{number}` | 围绕话题的讨论、劳动记录、按需任务属性 |
| 频道 | 仓库路径下，具体模式待定 | 属于邻接模块，不在本轮扩展设计 |

- **已确认**：点击任意看板卡片，打开**独立 Issue 页面并更新 URL**；**不以右侧 Issue Drawer 作为默认导航**。
- **已确认**：两种看板使用相同 GitHub Issue 集合和 `status:*` 语义，进入专注页时继承适用的筛选/排序参数；这些条件以 URL 为可分享、可刷新、可用 Back/Forward 恢复的状态来源。
- **已确认**：独立 Issue 允许外部链接直达、刷新及浏览器前进/后退。浏览器返回原看板后应恢复 URL 所表示的过滤与排序；尽量恢复此前浏览位置（具体恢复策略待验证）。
- **沿用约束**：URL 只是资源位置，不代表 GitHub 登录、仓库授权或写权限。

## 3. 仓库首页（已确认）

**第一版项目主页层级：Title / 简短介绍 → 团队成员头像与悬浮详情 → Repo 动态。项目主页不展示 Board。** 看板保留为独立 Kanban 页面，后置实现。

1. 顶部展示仓库/项目名称和**类似 README 的简短背景**，提供阅读完整 README 和 GitHub 仓库的入口；不将整篇长 README 占满首屏。
2. **团队成员**：展示成员头像；悬停头像时从 Repo 根目录的 `team-member.json` 读取并展示该成员的详细信息。项目参与者可手动维护文件；通过平台编辑时，由 GitHub App Bot 身份提交文件变更，服务端先校验发起人的仓库写入权限。JSON 字段契约待实现前确定。
3. **Repo 动态**：读取所展示 GitHub Issue 的第一楼（Issue body），将其作为 Markdown 文档渲染，并支持平台扩展格式，包括视频外链；Issue 评论仍用于讨论，不替代第一楼正文。每条动态应保留原 Issue 的来源链接。
4. 不以推测的完成百分比或进度条替代真实的状态和记录。
5. 第一版项目主页不显示 Board 预览，也不提供嵌入首页的看板交互。看板保留为独立 Kanban 页面，后置实现。

**待验证**：Title 区具体高度、README 展开方式、限高值、列内/整体滚动、动态列表的可见性与性能、移动端布局。

## 4. Kanban 专注页与 Board 规则（后续阶段）

本节保留已确认的独立看板设计约束，供后续实现使用。第一版项目主页不展示看板，独立 Kanban 页面也后置实现。

### 4.1 布局、筛选、视图

- **已确认**：专注页给看板更充分的空间，允许更详细的任务信息和更完整的操作；它与首页预览**不是两套数据或独立保存的任务状态**。
- **已确认**：筛选与排序通过 URL 查询参数表示；相同数据与相同参数应有**确定性的共有默认顺序**，而不是每个用户悄悄看到不同排序。精确 URL 参数 schema、控件分组、专注页密度仍待设计。
- **已确认**：可在仓库配置中定义**团队共享视图**（配置文件/schema 待定）；个人可以通过链接/浏览器书签保留视图，不默许自动修改仓库配置。
- **已确认**：**同列卡片手动重排仅在当前页面会话中临时生效**，覆盖当下显示顺序；筛选/排序改变、刷新或重访 URL 后重置。**不保存跨用户/跨页面的私有持久化排列**，避免同一链接呈现无声差异。需要清楚标示临时排列状态。
- **已确认**：跨列拖动修改 GitHub Issue 的唯一受管状态 Label，且只改变相应的 `status:*`；不能顺带覆盖普通标签、版本标签或其他属性。变更须有授权检查、明确反馈与失败恢复。

### 4.2 Label 与状态语义

- **已确认**：`status:*` 为看板列依据，一个进入看板的 Issue 须有**且仅有一个有效状态**；列顺序可配置。无效/冲突状态不能被静默任意归列。
- **已确认**：`archived` 为默认不展示的独立归档；GitHub 的 Open/Closed 是**与看板 status 不同的维度**。Closed 默认隐藏，若纳入显示则考虑分页/明确入口。
- **已确认**：`version:*` 是**用户主动启用、默认关闭**的可选标签命名空间，支持**多选**。同一 Issue 可涉及多个版本，在正文中分别解释各版本工作；但 Issue **仅有一个整体 status**，不推出每个版本各自的 Done/Doing，也不自动将旧版本判定完成。
- **沿用约束**：`channel:*` 仍作为频道识别依据，但频道使用体验属于另行研究；同一有效 Issue 可以同时被看板与频道关联。

### 4.3 CardItem 信息层级

- **已确认的平衡默认密度方向**：任务标题与 Issue 编号、多个当前 Assignees 的头像/身份、**最新有效 Labour Record 的 outcome 与记录作者**，以及**累计已登记的主观工时**（不能视为客观实际投入）。
- **已确认**：紧凑模式可隐藏较长的成果行和最近贡献者信息，不应虚构缺失的成果、参与者或完成进度。
- **尚待确定**：无 outcome 时是否回退展示 `work` 的片段、是否显示 Branch（仅在有可靠来源时）、专注页增加哪些字段以及默认卡片尺寸。

## 5. Issue 详情：社区交流优先（已确认）

- **已确认**：独立页面路由 `/{owner}/{repo}/issues/{number}`；**不是**点击看板后在原页面右侧展开的详情抽屉。
- **已确认**：Issue 页面以**社区交流和劳动进展**为主视觉，借鉴 Discord 的话题参与感，避免复制 GitHub Issue 的完整任务管理界面。
- **已确认**：左右侧栏**默认均隐藏**，且可独立展开。左侧用于项目工作区导航；右侧用于任务属性（status、Assignees、版本、标签等），让用户按需进入更像任务管理的体验。侧栏展开不改变 Issue URL。
- **已确认**：主内容包括话题标题/身份、简洁的最近劳动成果与工时摘要、原始 Issue 正文/话题背景，以及下方固定位置的两个 **Tab：讨论 / 劳动历史**。两者在同一页面切换，不将劳动记录重复混入普通讨论流。
- **已确认**：讨论消息强调作者、时间、自然的对话流，**不伪装成实时 IM**；内容来自 GitHub Issue 普通评论，保留原始来源及必要的加载/刷新反馈。是否默认折叠较长话题正文仍需检验。
- **已确认**：**讨论输入采用靠近讨论底部的 Discord 式可达位置 + 明确的 GitHub 提交反馈**：默认简洁、展开多行 Markdown，提交有写入中/成功/失败状态。究竟固定在视口还是内容底部、草稿如何自动恢复仍待原型验证。
- **已确认**：**劳动历史 Tab 使用独立结构化登记表单**；提交的数据写回 GitHub 允许的评论路径，并由 Labour Record 解析器识别。手动通过 GitHub 添加符合**最新劳动记录协议**的 YAML 评论与 UI 表单生成记录应能被同等读取，不强制劳动者必须通过 UI 填写。
- **已确认**：劳动历史贡献者和当前 Assignees 不是同一集合，不能因为某人登记劳动就自动赋予当前 Assignee 身份。有效 Labour Record 的历史贡献者依记录作者归属，记录需允许关联原 GitHub 评论。

### 阅读位置（本地 KV）

- **已确认**：首次打开 Issue，从话题上下文顶部开始；再次访问优先接续之前阅读的讨论，若出现新回复则优先定位到第一条未读回复，并可看见未读分界线。
- **已确认**：阅读进度**仅保存在当前浏览器本地 KV**，不写 GitHub、也不跨浏览器/设备同步；键应至少区分仓库、Issue，以及适用时的当前用户身份。
- **已确认**：不要在页面加载时直接将全部内容自动设为已读；应以用户实际可见的阅读位置更新。无本地数据时退回首次访问体验，用户可随时回到话题顶部。
- **待验证**：最后已读评论 ID、最近浏览时间、滚动锚点等具体 KV schema，以及讨论/劳动 Tab 的阅读位置是否分别记忆。

## 6. Assignees、Contributors、劳动与异常

- **已确认**：**Assignees** 表示目前正在参与该 Issue 的人，可以是**多人**；使用 GitHub 已有的 Assignee 权限模型。具备 GitHub 权限的用户可以管理符合资格的 Assignees；不设计额外的独立“认领”安全模型。
- **已确认**：**Contributors** 表示历史上通过可识别劳动记录登记过工作的贡献者，**即使后来不再是 Assignee，仍保留贡献历史**。它与 GitHub 仓库层面的 Contributors 统计不能混同。
- **已确认**：Doing 中无 Assignee 是**可审计异常**，提供提示/筛选但**不自动补人或修复**；Todo 未分配是正常情况。
- **已确认**：累计工时仅统计有记录的**主观估计登记工时**；没有数据不意味着没有劳动，不自动推断真实工时、完成度或不存在的 `outcome`。
- **沿用约束**：劳动数据可涉及 GitHub Issue 结构化评论及 Commit 记录；具体解析服从**更新的独立 Labour Record 协议**，不直接用旧版 MVP 文档的 YAML 示例反推严格格式。

## 7. 关键交互与反馈边界

| 情境 | 行为契约 |
| --- | --- |
| 点击独立 Kanban 页面中的卡片（看板实现后） | 导航到独立 Issue URL；返回恢复 URL 驱动的过滤/排序 |
| 跨列拖动 | 授权后仅写入 GitHub `status:*`；有提交中/确认/失败反馈，失败恢复原状并可重试 |
| 同列拖动 | 仅临时调整当前视图顺序，不写入 GitHub，也不产生跨页面持久排列 |
| 发表普通评论 | 通过 GitHub 授权路径写入；写入前后明确反馈，不提前显示为已持久成功 |
| 登记劳动 | 在劳动 Tab 使用结构化表单，写入符合最新劳动协议的 GitHub 记录；失败保留用户输入 |
| 无权限 / GitHub 未登录 | 公开内容可读；写操作按真实权限提示登录/授权/缺少权限，不能假装写入 |
| 空配置 / 无匹配 Issue / 加载失败 | 给出可理解的空态、重试/恢复路径，区分“没有记录”与“读取失败” |
| 缓存过期 / 分页 | 告知数据新鲜度与刷新能力；不能以缓存快照假装实时成功 |

以上属于应落实的交互契约；具体组件、网络时序及验证用例还需要结合实现/原型审查。

## 8. AI-native 后续特色能力（不是本轮 MVP 承诺）

- **已确认的未来方向**：页面可展示项目/当前话题的**基本背景与近期动态摘要**，右侧侧栏可以呈现**Agent 对话窗口**；基于用户 Profile 的个性化建议属于更远期方向。Agent 与任务属性侧栏如何共存**未定**。
- **已确认的初步实验边界**：最小 Context Harness 自动带入项目背景和当前浏览页面；用户**自行配置 API Key（BYOK）**，明确标识“实验/测试”；只保存在当前浏览器本地，更换浏览器/设备或清空本地数据需重新配置。
- **待调研**：Vercel Function 是否适合作为简单的 Chat Stream 转发层、流式协议/供应商兼容、密钥处理及成本、权限、上下文范围、来源可信度、日志防护与用户告知。**本地保存 Key 不等于本地推理**：代理方案仍会向服务端及模型供应商传输必要内容。
- **边界**：初期 Agent 仅辅助阅读、总结和问答，**不默认赋予 GitHub 写入能力**；不能将未验证方案写作当前已具备的能力。

## 9. 尚未确定、下一轮才需要评估的事项

1. **Kanban 专注页**：工具栏层次、完整卡片额外字段、默认/紧凑密度、桌面与触屏拖拽反馈和大数据量下的滚动。
2. **首页不含 Board**：验证 README 摘要长度、`team-member.json` 的字段/悬浮信息层级，以及 Issue 正文 Markdown/视频外链扩展渲染的边界与失败回退。
3. **导航细节**：从首页/专注页进入 Issue 后保留返回来源、URL 查询参数精确命名、浏览位置锚点恢复。
4. **Issue 主体**：长正文默认展开/折叠、讨论输入框是否 sticky、左右面板窄屏行为与草稿保持。
5. **劳动记录协议接入**：由最新独立协议确定字段/格式与解析边界；验证 GitHub UI YAML 路径和 LabourChain 表单路径一致性。
6. **配置**：共享视图配置的实际文件位置/schema、标签异常处理与各类 GitHub 只读/写入限制。
7. **验证**：真实可交互原型的加载、空态、权限、失败重试、键盘可达性、直接链接与浏览器历史的认知走查。

**后续工作优先级**：第一版先完成项目主页内容、成员悬浮详情与 Issue 正文扩展渲染。独立 Kanban 页面保留现有设计，后置实现；实现时再验证 Kanban → Issue → 返回的完整链路。不要将 #20 的跨仓库社区愿景或未来 AI 能力混入本次 MVP 交付范围。
